# cspub 开发文档与踩坑记录

> 条目格式：现象 → 排查铁证 → 修复方案 → 复用配方。只收实测验证过的条目。

## 1. OBS 上传返回"HTTP 200 + 0 字节"空图

**现象**：图片转存链路走通（签名接口返回正常、OBS 上传返回 200），但图床直链打开是 0 字节空文件，正文图裂。

**排查铁证**：CSDN 图床签名接口响应里 `customParam.isAudit` 字段是 **JSON 数字**（如 `"isAudit":1`），而 cspub 最初用只认字符串的 `jsonStr` 取值，取到空串；把空的 `x:isAudit` 表单字段发给华为 OBS multipart，OBS 接受请求（200）但生成的对象是 0 字节。表象完全像"请求被网关吞了"，实际是签名回调字段没取到。

**修复方案**：新增 `jsonScalar`（util.cj）——按 JsonKind 分派取值（字符串/数字/布尔字面量各走各路），`x:isAudit` 固定给 `"1"`。

**复用配方**：对 CSDN/华为 OBS 这类"前端烙死"的接口，**取 JSON 字段永远按 Kind 取，不要假设类型**；调试上传类接口时，先核对"签名响应里每个字段的实际 JSON 类型"，再核对"OBS 收到的每个表单字段值"。

## 2. CSDN 防盗链的真面目：HTTP 200 + 0 字节

**现象**：站外图 `<img>` 直连，状态码 200 看似正常，图片不显示。

**排查铁证**：`curl` 拉外链图返回 200 但 body 0 字节；同一 URL 换 UA/Referer 依旧。结论：CSDN 在网关层剥掉站外图响应体，常规"URL 有效性检查"手段全部失效。

**修复方案**：唯一解法是把图转存为站内图（csdnimg.cn 直链）。cspub 的转存流水线：扫描（代码围栏内跳过）→ 分流（内网/回环拦截、CSDN 图床/data: 跳过）→ 下载（拒绝 30x、单张 12 MiB 上限）→ 图床签名上传 → 从后往前回写（防偏移挪位）→ best-effort 不阻断发文。

**复用配方**：任何"发到 CSDN 的内容里带图"的需求，都必须走转存，不要赌外链；处理图片引用时，代码围栏内的 `![]()` 是示例文本，必须跳过。

## 3. TLS 信任：CSDN 证书链过不了 stdx 校验

**现象**：`https://blog.csdn.net` 的请求在 stdx TLS 下报 unknown CA；本机 1.0.5.1 与 1.2.0.1 两代 stdx、默认模式与 CustomCA 模式（内嵌逐字节一致的 Certum 根）全报；而系统 curl 验同一条链通过。

**排查铁证**：同一证书链，curl OK / stdx NG；CustomCA 内嵌根与链根逐字节一致仍 NG → 排除"根没带对"，指向 stdx 动态加载的 OpenSSL 验证行为问题（已记录待查，非本工具可修）。

**修复方案**：`--insecure`（TrustAll）作为显式逃生口。**正式发文先试默认模式，失败再加 `--insecure`**——HTTPS 内容仍加密，只是不验服务器身份，风险自担；不要默认带上。

**复用配方**：遇到"curl 过、stdx 不过"的证书问题，先对比两者加载的 OpenSSL 与信任来源，再考虑 TrustAll 逃生口；不要徒劳地反复换根证书。

## 4. stdx 1.2.0 的 TLS API 编译差异

**现象**：stdx 升到 1.2.0.1 后编译不过。

**排查铁证**：三处——① `CertificateVerifyMode` 移到 `stdx.net.tls.common` 子包；② 变体要求限定名（`CertificateVerifyMode.TrustAll`）；③ `CustomCA` 收 `Array<Certificate>`（接口），而 `X509Certificate.decodeFromPem` 返回 `Array<X509Certificate>`（类），Array 不协变。

**修复方案**：显式 `import stdx.net.tls.common.*`；变体写限定名；接口数组显式逐元素搬移（`for` 循环 append，不要强转）。

**复用配方**：stdx 大版本升级先看 TLS 子包结构变化；接口数组 vs 类数组的协变问题统一用显式循环搬移解决。源码以 1.2.0 为准，1.0.5.1 下这几处编译不过。

## 5. UTF-8 字节语义：汉字别按字节切

**现象**：摘要截断后出现乱码；行内渲染后部分汉字变非法序列。

**排查铁证**：截断点落在多字节序列中间；逐字节 `append` 把 3 字节汉字拆开。

**修复方案**：截断按首字节判界（`(b & 0xC0) != 0x80` 回退到边界）；行内渲染按区间整体转码（`Utf8View`/区间切片），不逐字节 append。

**复用配方**：仓颉里 String 的 `text[i]` 是 Byte——**凡是"按字符处理中文"的场景，一律按 UTF-8 边界切**。

## 6. 本机构建运行缺 stdx 动态库

**现象**：直接执行 `target/release/bin/main` 报 `error while loading shared libraries: libstdx.encoding.json.so`。

**排查铁证**：产物动态链接 stdx（cjpm.toml 未走静态段），运行时找不到 stdx so。

**修复方案**：
```bash
export LD_LIBRARY_PATH=<stdx>/dynamic/stdx:<cangjie>/runtime/lib/linux_x86_64_cjnative:<cangjie>/third_party/llvm/lib
```

**复用配方**：先补 LD_LIBRARY_PATH 再怀疑构建；发布产物（dist/ 包）不含此问题——打包时静态链接或在包内附 runtime 说明。

## 7. 百家号纯 Cookie HTTP 发文走不通（React 事件链）

**现象**：拿浏览器 Cookie 直调百家号发布接口 `/rest/2.0/elite/article/publish`，稳定返回 HTTP 500；`builderinner` 官方接口要 `app_id`+`app_token`，而开发者入口 2026 年起是定向邀请制，普通账号后台没有「开发」菜单。

**排查铁证**：①baijiahao-auto skill（2026-04 实战）记录发布按钮是 React SPA 组件，点击需经 `preCheck→paramProxy→re()` 完整事件链——连 CDP 代理的原生 `click()` 都只能触发"保存草稿"，触发不了发布（已知限制 #5）；直调 API 缺 CSRF token 等完整参数必 500（#12）。②社区所有可用实现（baijiahao-publisher、opub、omnipost、PostFlow）无一例外走 Playwright 浏览器自动化，没有一个纯 HTTP 发布成功先例；连编辑器"存草稿"的 HTTP 端点都没有公开可用记录。

**修复方案**：cspub 的百家号做双通道——有开发者凭证走官方 token 接口（`src/baijiahao.cj`）；否则 Cookie 走浏览器自动化伴生脚本 `scripts/baijiahao_publish.py`（Playwright：Cookie 注入 → `builder/rc/edit?type=news` → 关 `.cheetah-tour` 弹窗 → `input.cheetah-input` 上 execCommand 填标题 → `#ueditor_0` iframe 里 `editor.setContent` + `fireEvent('contentchange')` + `sync()` → 点「存草稿/发布」）。凭证经临时文件传给子进程，用完即删。

**复用配方**：凡是"React 后台 + 无公开 API"的平台（百家号/小红书/快手同款），别在纯 HTTP 上耗时间，直接浏览器自动化；标题受控组件用 execCommand、UEditor 改内容后必须 fireEvent+sync，这两个选择器/姿势是社区实测可复用的。

## 8. 百家号新版编辑器是 Lexical：选择器/注入姿势全变

**现象**：按社区旧配方（`input.cheetah-input` 填标题、UEditor iframe `setContent` 填正文）自动化百家号编辑页，标题框等不到、正文填不进；偶发正文内容整段出现在标题框（超 86/64 限制）。

**排查铁证**：①编辑区 DOM 带 `data-lexical-editor="true"`——新版换成了 Meta Lexical 框架，`execCommand`/合成 ClipboardEvent 一概不生效；②标题与正文是**两个同名 class 的 Lexical 编辑器**，`querySelector` 取第一条匹配拿到的是标题框——"正文贴进标题（86/64）"就是这条；③headless 下 `navigator.clipboard.write` + Ctrl+V 也不触发 Lexical 粘贴，**逐字键入（keyboard.insert_text，真实 beforeinput）实测可靠**；④`「确定 (1)」`按钮文案带计数，`get_by_text(exact=True)` 匹配落空；⑤AI 推广弹窗/「新增智能标题」气泡/已关闭弹窗的空 `.cheetah-modal-wrap` 时序不定地拦截点击，Playwright click 反复 retry。

**修复方案**（`scripts/baijiahao_publish.py`）：标题= `[data-testid='news-title-input'] [data-lexical-editor='true']`，正文=**不在标题框里**的 `data-lexical-editor`（`findIndex + closest` 区分）；二者都用 `keyboard.insert_text` 键入（正文为 `_plain(html)` 纯文本，富文本格式放弃）；键入后校验 innerText，失败重试 3 次 + DOM 直写兜底；每步前循环关弹窗（DOM click `button.close` + 含「立即体验」的包裹层整层隐藏 + 空包裹层去指针化）；发布走「选择封面」对话框 `input[type=file]` `set_input_files` 上传本地图，确认按钮用 `button:has-text('确定')` 包含匹配；成功判据必须校验标题与正文字数双非空，防空内容假成功。

**复用配方**：遇到 Lexical 编辑器（认 `data-lexical-editor` 属性）直接放弃合成事件路线，用真实键盘输入 + 点击后校验回读；同名 class 的多编辑器页面用 `closest(容器)` 区分而不是取 first；浮层拦截一律「JS 隐藏 + force click + 结果回读」三件套。

## 9. 掘金 ImageX 图片上传：直调签名必然被拒，改走真实浏览器通道

**现象**：掘金把正文相对路径图片渲染成 `https://juejin.cn/<路径>` 死链；转存需走字节 ImageX 五步链，但 `ApplyImageUpload` 稳定返回 `SignatureDoesNotMatch`（CodeN 100010）——同一份实现（Python 与仓颉签名逐字节对账一致）时而被接受、时而被拒，最终演变为长期被拒。

**排查铁证**：①旧接口 `/images_upload/v1/create` 已 404 下线，现行五步链配方来自 juejin-skills/mukun_md_push 社区逆向；②仓颉签名 == Python 签名（同输入逐字节一致），排除本地算法差异；③**浏览器抓包（决定性）**：在掘金编辑器里真实上传一张图，拦住发往 `imagex.bytedanceapi.com` 的 ApplyImageUpload，其 `SignedHeaders` 只有 `x-amz-date;x-amz-security-token`（**不含 host**），query 原序为 `Action,Version,ServiceId`（非字母序）；照抄这套组合重放仍被拒（详见④）；④**排除法穷举**：字母序/原序、带/不带 host、GET/POST、签不签 `x-amz-content-sha256`、sk 是否 base64 解码、`AWS4` 前缀有无、火山原生 `HMAC-SHA256` 变体，10+ 组合**全部** `SignatureDoesNotMatch`；而**同一时刻同一浏览器的上传一次成功** → 结论：网关按**客户端 TLS/UA 指纹**校验，不看签名内容本身；⑤旁证：`Credential` 的 scope 用令牌内 `LTAccessKeyId` 会改报 `CheckAuthenticationError`，用 `AccessKeyId` 才推进到签名比对 → AK 本身正确，问题只在「谁来发这个请求」；⑥gen_token 的 GET 带 `Content-Type` 会签发坏令牌（社区同款注释），属另一独立坑。

**修复方案**（`src/juejin.cj` + `scripts/juejin_upload.py`）：**主通道改为真实浏览器上传** —— playwright 携带 Cookie 打开 `https://juejin.cn/editor/drafts/new`，对每张本地图调用 file input 的 `set_input_files`，拦 `get_img_url` 响应取 `data.main_url`（即编辑器自己会写进正文的同一条地址），逐图输出路径→URL 映射 JSON；仓颉侧 `rehostJuejinImages` 优先调该脚本、脚本缺失时降级内置 `uploadJuejinImage`（ImageX 五步链 + CRC32 表 + SigV4）。gen_token/get_img_url 只带 UA+Cookie；Commit best-effort；单张失败保留原链接并提示，不阻断发文。

**复用配方**：①「AWS 签名逐字节一致却被拒」时，先抓浏览器真实请求对照 `SignedHeaders`/query 序，再穷举变体；**若真实浏览器能过而非浏览器客户端全灭，直接判为指纹校验，别再改签名**——换浏览器通道（playwright + Cookie + 拦响应取结果）是成本最低的解法，与百家号伴生脚本同一模式；②掘金编辑器上传后图片地址由 `get_img_url` 下发，直接取 `data.main_url` 即可，无需自己拼；③**该 CDN 直链对 `curl` 一律 403**（边缘返回 `TLB` 错误页，拦非浏览器客户端），验收必须用浏览器内 `img.naturalWidth > 0` 判定，别用 curl 状态码误判成「图片坏了」；④五步链固定形状备查：gen_token 只带 UA+Cookie、直传必须带 `Content-CRC32`（缺了报 4007）、`get_img_url` 参数名是 `uri`。

## 10. 掘金其实认外链：图片不必搬进平台图床

**现象**：按第 9 节的结论，掘金正文的本地图片只有两条路——浏览器通道（依赖 `python3 + playwright + chromium`）或直调 ImageX（被指纹校验拒死）。整条链路又重又脆，跑一篇要拉起一个浏览器。

**排查铁证**：①**样本反证平台并不限制外链**——`https://juejin.cn/post/7704394460696461350` 正文 3 张图全部是 AtomGit 仓库链接（`atomgit.com/api/v5/repos/qq8864/cj-tauri/raw/...?ref=main`），浏览器渲染 `loaded=True`；②**复验要走自己的发布通道**（编辑器手写与 API 建草稿是两条路径，不能只看别人的文章）：`cspub publish` 以 `article_draft/create` 建草稿 `7704389851194605594`，正文只放一条外链图，浏览器打开该草稿 → `loaded=True 3120x2080`，正文采样里就是 `![外链图](https://atomgit.com/api/v5/...)`；③**外链可匿名直取**：`.../qq8864/images/raw/cjh/arch-diagram.png?ref=main` → `HTTP 200`、`content-type: image/jpeg`、210777 字节，无需 Cookie/Referer。→ 平台图床只是「编辑器顺手自动上传」的默认行为，**不是渲染的前置条件**。

**修复方案**（`src/atomgit.cj` + `src/juejin.cj`）：掘金图片改三级降级——①**外链优先**：配了 `CSPUB_ATOMGIT_TOKEN` 就把本地图逐张 `POST /api/v5/repos/{owner}/{repo}/contents/{path}`（base64 内容 + 提交说明 + 分支），正文回写 `https://atomgit.com/api/v5/repos/{owner}/{repo}/raw/{path}?ref={branch}`；②①失败的图降级伴生脚本浏览器通道；③再降级内置 ImageX；三级都不成则保留原引用并提示，**best-effort 不阻断发文**。默认仓库 `qq8864/images`、分支 `main`、目录 `cspub`，可用 `CSPUB_ATOMGIT_REPO/BRANCH/DIR` 覆盖；令牌走 `Authorization: Bearer` 头，不落 URL。

**复用配方**：①**判断平台是否限制外链，别查文档也别看别人文章了事**——拿一条真实外链图走自己的发布通道（API 建草稿）再以浏览器内 `naturalWidth>0` 判定，因为「编辑器手写」和「API 写入正文」是两条渲染路径；②图床选型优先复用**自己已有的存储**（代码托管的 raw 链接），省掉整套平台图床签名链与浏览器依赖；③AtomGit 新建文件用**随机文件名**避坑——`contents` 对已存在路径返回 400，新建接口不复用旧文件，重名就得上 PUT 带 blob sha；④AtomGit 鉴权三种方式等价（`Authorization: Bearer` / `PRIVATE-TOKEN` / `access_token` 查询参数），选头方式，查询参数会把令牌留在 URL 里；⑤**仓颉块注释支持嵌套**：注释正文里写了 `image/*` 这种含 `/*` 的字样会再开一层注释，报 `unterminated block comment`——注释里别出现 `/*`。

## 11. 开源中国：官方 OpenAPI 走不通，站点自用 apiv1 + 自带图床才行

**现象**：要给开源中国（oschina.net）加发文通道，官方路线全线不可用——`/action/openapi/blog_pub` 要先注册应用拿 `client_id`/`client_secret`，再走 oauth2 换 `access_token`（授权范围还要 `password`），个人自用根本落不了地。退而直接打站点自己的 `apiv1.oschina.net`，带着浏览器登录后的 `oscid` Cookie 请求 `user/myDetails`，却被回 `{"code":40001,"message":"用户未登录，请先登录"}`（HTTP 200），看起来 Cookie 完全不认。

**排查铁证**：①**端点从编辑器 bundle 反查**：`www.oschina.net/blog/new` 只返回 3730 字节 SPA 外壳，必须在 `static.oschina.net/oschina/space/v2/js/` 的 `draftWriteType-*`/`create-*` chunk 里扒请求体——`I("/blog/web/add",c)` 的 `c` 里有 `title/content/contentType/type/catalog/privacy/disableComment/draft/user/isAiRelated`，草稿走 `"/api/draft/save_draft"`（同一个 `u` 对象但不带 draft/type），分类走 `"/blog_catalog/list_by_user"`；②**40001 是我自己的锅**：`cookie_kaiyuan` 文件里存的**已经是 `oscid=ESvQB0…` 整串**，我又按 `-b "oscid=$CK"` 拼了一次，服务端收到 `oscid=oscid=…` 自然认不出登录态；改成 `-H "Cookie: $(cat cookie_kaiyuan)"` 透传后同一端点立刻返回 `success:true` + `result.userId=4197674`，分类 `list_by_user` 也同步通了；③**图床端点靠探测**：候选路径里只有 `/oschinapi/upload/img` 返回 200（其余 `/upload/image`、`/file/upload`、`/api/image/upload` 全是 Spring 的 404 结构体），multipart 字段名 `file`，2MB 图片单请求即成功；④**直链「看着像坏的」其实好的**：返回 `https://oscimg.oschina.net//null/up-<md5>.png` 带着一段 `//null/`，裸 `curl` 取它得 403（146 字节 `TLB` 页、`text/html`）——换成浏览器 UA + `Referer: https://www.oschina.net/` 再取 → `HTTP 200`、`content-type: image/png`、130318 字节，与源图**逐字节一致**；⑤**草稿回读闭环**：`GET /api/draft/edit/detail?id=<draftId>`（query 传 id；改成 POST JSON 会回「草稿不存在」code 500）能拉回正文，看到图片已被回写成图床直链、Markdown 原样保留。

**修复方案**（`src/oschina.cj` + `src/main.cj`）：新增 `--platform oschina`——鉴权只透传 `oscid` 整串 Cookie，请求固定带 `Referer`/`Origin: https://www.oschina.net`；`userId` 缺配置时先 `GET /user/myDetails` 现查；分类按 `front-matter categories` 名匹配、匹配不到取账号第一个（也可 `CSPUB_OSCHINA_CATALOG` 直指）；正文以 `contentType: 1`（Markdown）原样提交，**不要预渲染 HTML**；图片优先级 = **平台自带图床 `/upload/img`（有 Cookie 就能用）→ AtomGit 外链兜底 → 保留原引用**，仍 best-effort 不阻断发文；成功判据 `code == 200` 且拿到 id（草稿 `result.id`、发布 `result` 标量）。

**复用配方**：①**本地 cookie 文件先看清是不是自带 `name=` 前缀**——`-b "oscid=$(cat file)"` 这种二次拼接会得到 `oscid=oscid=…`，服务端一律当未登录（408/40001 类错误先怀疑这一步，别怀疑 Cookie 失效）；②平台的「官方开放 API」要注册应用 + oauth2 时，直接反查它**自己前端调的内部 apiv1**（同 Cookie 同鉴权，请求头补齐 `Referer`/`Origin` 即可通），成本低一个数量级；③`static.*` 的 JS chunk 请求要带浏览器 UA + `Referer`，否则 CDN 直接 403，扒包时先补齐这两个头；④直链里出现 `/null/`、双斜杠别急着判死链——**验收一律带浏览器 UA 取回并和源图比字节**，无 UA 的 403 是 CDN 拦客户端，不是对象不存在；⑤同一平台「草稿」和「发布」常是两个端点、两种 `result` 形状（对象 `.id` vs 标量 id），解析函数要两者都吃；⑥`privacy` 这类布尔字段的语义别靠猜——语义没实测确认前做成可配置项并写清默认值，别把该公开的文章默默发成私密（或反过来）。

## 12. 发布接口回了 id ≠ 文章已公开：SPA 外壳与审核态

**现象**：开源中国 `--live` 正式发布一路绿灯——`/blog/web/add` 返回 `code: 200` + 博客 id `19787222`，`blog/detail` 也能读到完整正文与图片，但用户在浏览器打开的地址是「找不到您访问的页面」。更迷惑的是：同一地址 `curl` 永远拿到 `HTTP 200`，看上去「文章好好的」。

**排查铁证**：①**先怀疑自己拼的 URL**：原实现输出 `https://www.oschina.net/u/4197674/blog/19787222`，实测**服务端 404**（1548 字节错误页），而 `https://www.oschina.net/blog/19787222` 回 200——但把 id 改成不存在的 `999999999` 或写错一位的 `1978722`，返回**同样是 200 + 3730 字节**，说明这是 SPA 外壳路由（任何 id 都回同一份外壳），**状态码根本不能判活**；②**改判据为浏览器渲染**：playwright 打开 `https://www.oschina.net/blog/19787222`，`document.title` 是「找不到您访问的页面」、正文长度 113、`oscimg` 图 0 张——带登录 Cookie 再渲染结果一致，排除「游客不可见但自己可见」；③**内容确实已入库**：`GET /oschinapi/blog/detail?id=19787222` 回 `code:200`，`contentType=1`、`catalog=6616684`、正文是服务端渲染后的 HTML（`<h2>/<p>`），3 张图已是 `oscimg.oschina.net//null/up-<md5>.png` 且三张直链均 200、617773/705372/259509 字节与源图**逐字节一致**；④`ident` 字段为 `null`（未生成 slug）、`folder=99`——推断为**新号/首篇走人工审核**，发布即入库、审核通过才公开。

**修复方案**：①`oschinaArticleUrl` 改为 `${OSCHINA_SITE}/blog/{id}`（去掉 `userId` 参数，单测断言同步改）；②CLI 输出与 README 明确「发布成功≠立刻公开」，提示审核态需稍后复验；③验收流程固定为「接口取正文与图 → 浏览器渲染判标题/正文长度/图 `naturalWidth`」，不再用 `curl` 状态码当凭证。

**复用配方**：①**现代 SPA 站点的 200 毫无信息量**——路由外壳对任意 id 都回 200，判「文章/资源是否存在、是否公开」必须用浏览器渲染（`document.title`、`body.innerText` 长度、`img.naturalWidth`）或调后端详情接口；②发布类接口返回 id 只证明「写入成功」，**公开可见性要单独验一层**（新号、首篇、含外链/敏感词都可能触发审核），别把 id 当上线凭证；③同一平台的「详情路由」和「列表/详情接口」往往两套 id 语义（数字 id vs slug `ident`），`ident` 为 null 常意味着尚未走完发布/审核流程；④文档与 CHANGELOG 里对未闭环的验证要**明写「待确认」并留下复验方法**，别把「接口 200」写成「已上线」。

## 13. 图片转存全失败会静默发出死链文，`imgs` 预演还帮着骗人

**现象**：掘金首发（`7704603488899366939`）5 张图全部转存失败，CLI 打了 5 行 `⚠ 掘金图片转存失败（保留原引用，网页上会显示死链）` 加一行 `图片转存：5 张待转，成功 0，失败 5`，然后**照常把草稿建完**，线上文章五张图全是裂图。排查时先用 `cspub imgs` 预演，输出却是 `skip (not http)`，看着像「这些图本来就不用转存」，进一步把人带偏。

**排查铁证**：①`rehostImages`（`src/images.cj` 本地路径分支）对非 http 引用走的是「读本地文件 → 上传图床」，实际会传，与 `imgs` 的 `skip (not http)` 标签直接矛盾——标签只判「是不是 http」，不认本地绝对路径；②同一批文件两处结论相反：旧二进制的 `imgs` 输出 5 条 `skip (not http)`，而发布日志同时打出「掘金：上传正文图片 5 张」；③真正决定「发出去会不会裂图」的判据是**转存后的正文**里还有没有非 http 引用（`hasLocalImages`），而当时只有开源中国一条链路调了它，其余四个平台没人管；④失败计数打了一行字不等于用户收到告警——五个平台各打各的计数，没有统一收口。

**修复方案**：①`imgPreviewAction`（`src/images.cj`）把预演标签纯函数化：本地绝对路径 → `upload (local file)`，`imgs` 与真实发布共用同一份判定；②`localImageCount` + `imagesRemainGate(platform, md, strict)` 四平台统一收口：转存后正文仍有本地图就打 `⚠⚠` 横幅（写明后果与排查方向），配 `CSPUB_STRICT_IMAGES=1/true/yes` 时返回 true 让调用方 `return 1` 中止，默认仍是 best-effort 照发；③删除被取代的 `hasLocalImages`，其单测用例整组迁进新测试，用例不丢。

**复用配方**：①多平台 CLI 里每个 rehost 函数各打各的计数**不构成告警**，必须有一个统一收口点把「这篇会裂图」翻译成醒目结论；②预演/试运行子命令必须与真实发布走**同一份判定逻辑**（否则预演本身变成误导源），能抽成纯函数就别复制分支；③「是否还会裂图」的判据放在**转存后的正文**上，别信转存函数自己的计数器（跳过的、降级成功的都算不清）；④改行为优先「默认不变 + 环境变量开严格」，一次改动别顺手打断既有的 best-effort 习惯。

## 14. 伴生脚本硬编码相对路径：只有站在仓库根目录才跑得动

**现象**：`--platform baijiahao` 在文章目录里跑，直接报「找不到伴生脚本 `scripts/baijiahao_publish.py`（须在 cspub 仓库根目录下运行）」。掘金图片通道同款问题，但更阴：找不到 `scripts/juejin_upload.py` 就静默降级到内置 ImageX 实现，而 ImageX 直调签名必然被拒（§9），于是**换个目录运行 = 图片全失败**，代价只在日志里留一行 ⚠。

**排查铁证**：①两处调用点都是 `let scriptPath = "scripts/xxx.py"` 再拿 `readTextFileAll` 探测，路径按进程 cwd 解析，与二进制装在哪无关；②从 `/root/test/cj` 跑掘金：出现「⚠ 掘金图片上传脚本不存…降级仓颉内置 ImageX 实现」→ 5 张全失败；③同一条命令在仓库根目录跑 5/5 成功——变量只有 cwd。

**修复方案**：`resolveCompanionScript`（`src/util.cj`）按优先级返回第一个可读候选：①`CSPUB_SCRIPT_DIR` 显式指定；②当前目录的相对路径；③**可执行文件目录起向上回溯 5 级**的 `scripts/<name>`。可执行文件目录用 `canonicalize("/proc/self/exe")` 解析符号链接取得（不依赖 argv[0]），非 Linux 取不到就只走前两个候选。百家号、掘金两处调用点改用该函数，找不到时把三个查找位置与两种修法一起打印出来。候选列表抽成纯函数 `scriptCandidates`，单测不碰文件系统。

**复用配方**：①随二进制分发的伴生文件（python 脚本、模板、数据）**不要用裸相对路径**，按「环境变量 → cwd → 可执行文件目录回溯」三层解析；②Linux 上取自身位置用 `/proc/self/exe` + `canonicalize` 最稳（argv[0] 可能是相对路径或被改写），跨平台留空串降级即可；③「找不到脚本」的报错要直接给出候选路径与修法，别让用户猜 cwd；④降级路径要显眼——本案的降级不是「功能变弱」而是「功能全坏」，一行 ⚠ 挡不住。

## 15. GitHub Actions 全程 `startup_failure`：真因是账户邮箱未验证

**现象**：官网起先走标准 `actions/deploy-pages` 写法（`.github/workflows/pages.yml`：`configure-pages@v5` + `upload-pages-artifact@v3` + `deploy-pages@v4`，`permissions: pages/id-token: write`），push 后 workflow run 状态 `startup_failure`：**jobs 为 0 个**、`name` 字段空、无任何 annotation 或日志。后续删掉自写 workflow 改走 legacy 分支发布，连 GitHub **内置**的 `dynamic/pages/pages-build-deployment` 也照样 `startup_failure`（Pages 状态 `errored`、`Page build failed.`），站点首页长期 404。

**排查铁证**：①`GET /actions/permissions` → `enabled: true`、`allowed_actions: all`、`sha_pinning_required: false`，Actions 没被禁；②`GET /actions/workflows` → 文件被识别、`state: active`，GitHub 已成功解析 YAML（本地 `yaml.safe_load` 同样通过）——不是语法问题；③`environment github-pages` 已被自动创建且清空 `branch_policy`（rules `[]`），排除环境保护；④把默认 token 权限 `read` → `write`（`PUT /actions/permissions/workflow`）重跑仍失败，排除 token 权限；⑤**跨仓对照是决定性一击**：同一账户下的 `cjh` 仓库 `dynamic/pages/pages-build-deployment` 是 `success`（首页可访问），而 `cspub`、`cj-tauri` 全部 `startup_failure`；三仓 `actions/permissions`、`rulesets`、`runners`、`default_branch`、可见性逐项一致——**说明不是 YAML、不是仓库配置，是启动闸门层面的东西**；⑥换发布源也无效：`gh-pages` → `main` 的 `/docs` 仍 `startup_failure`；想用 `/website` 被 API 直接拒（`/website is not a possible value. Must be one of the following: /, /docs`）；⑦`DELETE /pages` 回 422、`POST /pages` 回 409「already enabled」，站点无法重置。

**修复方案**：账户侧**验证邮箱**（GitHub 对未验证邮箱的账户静默拒绝启动 Actions）。验证后无需改任何配置，直接 `POST /repos/{o}/{r}/pages/builds {"build_type":"legacy"}` 再触发一次，run 状态立刻按 `startup_failure` → **`waiting`** → `in_progress` → `completed/success` 走完，`GET /pages` 变 `status: built`，首页 `200`。

发布形态最终定为 **`gh-pages` 分支根目录**：临时目录 `git init -q -b gh-pages` → `cp -r website/. .` → `touch .nojekyll` → 提交 → `push <github> gh-pages:gh-pages --force` → `PUT /pages {"build_type":"legacy","source":{"branch":"gh-pages","path":"/"}}`。`website/` 是唯一源码，`docs/` 保持纯文档目录不掺站点产物（排查期曾把产物复制进 `docs/` 走 `/docs` 发布，确认可行后回退）。

**复用配方**：①**`startup_failure` 且 `jobs == 0`、无任何日志时，第一件事查账户邮箱是否已验证**（Settings → Emails 有 Unverified 提示），这是 GitHub 最典型的「悄悄不跑」条件，别再改 YAML、别再折腾 environment/权限，那些都不产出可观察差异；②**跨仓对照是最快的定位手段**：同账户随便找一个 Actions 跑得动的仓库对比 `dynamic` 内置 workflow 的结论，一边 success 一边 startup_failure 就能立刻排除语言/配置/权限三个方向；③GitHub 分支发布的 `source.path` **只接受 `/` 与 `/docs`**，传别的目录 API 会 422 并把合法值列给你，别按「任意子目录」设想设计仓库结构；④`DELETE /pages` 并不是可用的重置手段（站点处于 errored 时回 422，重建回 409），要修就修根因，别指望推倒重来；⑤排查期改过的仓库级设置（token 默认权限）要记得回退到与正常仓库一致的值并在记录里写清，避免留下「为了排查而改」的残留。

## 16. 六平台批量发同一篇时炸出来的三件小事：headless shell、单图超时、文件名骗人

**现象**：用同一篇带 2 张官网外链图的文章依次发 CSDN / 知乎 / 掘金 / 开源中国 / 百家号，五个平台全部回显 id 或草稿地址，但过程中各冒出一个问题：①百家号调起浏览器自动化时先报 `BrowserType.launch: Executable doesn't exist at /root/.cache/ms-playwright/chromium_headless_shell-1223/chrome-headless-shell-linux64/chrome-headless-shell`，并打出 Playwright 的「Please run playwright install」横幅；②CSDN 首次 `publish` 时图片转存 `成功 1 / 失败 1`，失败那张报 `Read body timeout and the connection is closed.`，文章仍照发（正文保留原外链）；③准备博客园凭证时发现本地 `cookie_bokeyuan` 文件内容是 `HMACCOUNT=96…`——**百度统计的 cookie**，跟博客园毫无关系。

**排查铁证**：①headless shell 失败后脚本自己降级用完整版 chromium，同一轮就打出 `[RESULT] success: mode=draft page=https://baijiahao.baidu.com/builder/rc/edit?type=news&is_from_cms=1`，说明缺的只是 `chromium_headless_shell-1223` 这个瘦身二进制，`chromium-1181/chrome-linux/chrome`（458 MB）本身完好；②CSDN 那次失败是**单张**图片下载超时（同一轮另一张 130 KB 的图正常转成 `i-blog.csdnimg.cn/direct/…png`），不是签名或图床故障，重试即成功——用 `--update 170149149773` 重跑同一篇，输出 `图片转存完成：成功 2 / 失败 0`，两张图都换成了 `i-blog.csdnimg.cn` 直链；③博客园那条是**凭证来源错误**而非工具缺陷：`cspub` 对博客园只认 `CSPUB_CNBLOGS_BLOG_ID/USERNAME/TOKEN`（MetaWeblog 访问令牌），cookie 文件里既无 blogId 也无 token 字样，`whoami cnblogs` 当场报缺字段。

**修复方案**：①百家号不需要额外动作——伴生脚本已内置「headless shell 缺失 → 降级完整 chromium」的分支，只要 `PLAYWRIGHT_BROWSERS_PATH` 指向的目录里有 `chromium-*` 就能跑通；反过来若想真正用上 headless shell，补一次 `playwright install chromium` 即可，属于可选优化；②图片转存超时按 best-effort 语义处理：文章先发出去（不因为一张图卡住），随后 `cspub publish <同一篇> --platform csdn --update <id>` 重跑，图片转存会重走一遍并把正文里的原外链替换成图床直链，**更新不占当日发文额度**；③博客园要发就去后台「设置 → 允许博客客户端访问」重新生成访问令牌，把博客名 / 登录名 / 令牌分别填进三个环境变量或 `~/.cspub/config.json` 的 `cnblogsBlogId` / `cnblogsUsername` / `cnblogsToken`。

**复用配方**：①**Playwright 报 `chromium_headless_shell-*` 缺失不等于浏览器没装**——新版 Playwright 默认只想用 headless shell，`playwright install` 或 `PLAYWRIGHT_BROWSERS_PATH` 下存在完整 `chromium-*` 就够，别急着重装整条工具链；②**图片转存失败先看是不是"单张超时"**：单张失败 + 其余成功 + 报错是 `Read body timeout` 时，重跑比改代码有效，尤其是图源在境外 CDN（GitHub Pages）时；③**`--update` 是图片补齐的后门**：首次发布丢图不必删文重发（CSDN 每日仅 1 篇额度），原地更新即可重走转存链路；④**凭证文件名不能当证据**：名字里带 `bokeyuan` / `zhihu` 的文件可能是别的站点的 cookie（本次那份是百度统计 `HMACCOUNT`），发之前一律用 `cspub whoami <platform>` 验字段，只验格式不联网，零成本。

## 17. 正文图片全是外链时百家号发不出去：封面取不到本地图

## 18. 腾讯云 addArticle：先校验参数再校验登录，成功响应里根本没有 `code`

**现象**：实测 `POST https://cloud.tencent.com/developer/api/article/addArticle` 时，空 JSON `{}` 返回 `HTTP 400 {"msg":"参数错误","code":400}`；把标题/正文/专栏等字段补齐后再发，返回 `HTTP 401 {"msg":"你还未登录，请先登录","code":401}`。真发成功时响应体是 `{"articleId":2650368,"status":0}`——**里面没有 `code` 字段**。

**修复方案**：①**字段一次给全再测鉴权**——本地先把 `title` / `content`(HTML) / `plain` / `summary` / `userSummary` / `sourceType:1` / `isOriginal:true` / `classifyIds:[...]` / `openComment:1` / `closeTextLink:0` 组装完整，再发请求，避免把参数错 400 误判成 Cookie 失效；②成功判据改成「响应能解析出 `articleId`」，绝不写 `code == 0`（成功体里取不到 code，那样写会把成功判成失败）；③错误映射里 400 与 401 给不同提示，400 引导去查专栏/正文字数，401 才引导去重新登录；④`skey`、`qcommunity_session` 直接拼 Cookie 头，不做 URL 编码。

**复用配方**：①**「参数校验先于登录校验」的接口，空体测试不能用来判断凭证死活**——必须给全字段再看 401，这是判断登录态的唯一正确姿势；②**成功响应没有 `code` 时按字段存在性判成功**（本例判 `articleId`），把「取不到 code」当成失败是最容易写错的一种成功判据；③正文下限按 **UTF-8 字符**算（140 字），按字节算会把 47 个汉字当成「够长」；④专栏 `classifyIds` 必须是**非空数组**，新账号要先在社区后台建专栏（审核 1~3 个工作日，每用户上限 9 个），空数组必 400。

## 19. 语雀：namespace 单段必 404，非法公开性会被「兜底成 0」悄悄发成私密

**现象**：①把 `CSPUB_YUQUE_NAMESPACE` 填成知识库名（单段，例如 `cspub`）时接口返回 404，很容易被当成「Token 没权限」去反复重发 Token；②`CSPUB_YUQUE_PUBLIC=abc` 这类脏配置，首版实现里被解析成 **0（私密）**，于是本该公开的文章静默发成私密文档。单测 `yuquePublicParseTest` 首轮就是因此红的。

**排查铁证**：①官方 spec 把 `404` 明确写成「实体未找到」、`403` 才是「无操作权限」，且创建接口路径是 `/api/v2/repos/{group_login}/{book_slug}/docs`——**两段式**，单段名根本没有对应路由；②单测实测 `parseYuquePublic("abc")` 返回 `0` 而不是 `-1`，根因是它借用了「非数字返回 0」的 `yuqueNum` 兜底，而 `0` 在语雀语义里是合法的「私密」。

**修复方案**：①`yuqueNamespaceValid` 在发请求前本地校验两段式（`split("/")` 长度必须为 2 且两段非空），单段直接报错并说明「取知识库 URL 里那两段」，不拿注定 404 的请求去怀疑 Token；②`parseYuquePublic` 不回落到 `yuqueNum`，自己 `Int64.parse` 失败即返回 `-1`（表示不传该字段、继承知识库公开性），只有 `0/1/2` 才原样透传；③`--draft` 显式建 `public=0` 私密文档（语雀的私密文档就是草稿态，可在网页端改公开），`--live` 才用配置值或不传。

**复用配方**：①**枚举语义里的「校验兜底成 0」是 bug，不是容错**——0 常常是合法枚举值（此处=私密），非法输入必须走独立的 `-1`/`none` 分支，否则脏配置会静默改变业务行为；②语雀创建文档**不会自动加入知识库目录**，文档本身已经存在且直链可访问，别把「目录里没有」当成创建失败；③语雀是当前唯一能用 `GET /api/v2/user` **真验证凭证**的平台（腾讯云/头条的 Cookie 只能真发一篇才知道），`whoami yuque` 因此会联网；④`format` 必须显式 `markdown` 且正文原样提交 Markdown 源文，不要像 CSDN 那样先渲染成 HTML。

## 21. SegmentFault：403 不是没登录而是 CSRF，Token 又根本不在 Cookie 里

**现象**：①网上流传的思否发文路径（`/api/article/create`、`/api/articles`、`/api/article/draft`）实测**全是 404**，容易得到「没有可用 API」的错误结论；②改用真实路径 `POST /gateway/article` 后拿到 **403「非法请求，请刷新页面后重试」**，第一反应必然是「Cookie 过期了」，于是反复换 Cookie——**方向完全错**；③思否的登录 Cookie 里**根本没有任何名为 token 的字段**，翻遍 Cookie 也找不到要放进请求头的那个值。

**排查铁证（2026-11-06，无 Cookie 实测鉴权语义）**：
- `POST https://segmentfault.com/gateway/article` → `HTTP 401 "Unauthorized"`（**路由真实、只差鉴权**）
- `GET https://segmentfault.com/gateway/article` → `HTTP 403 非法请求，请刷新页面后重试`（同一路径换方法，缺 Referer 就被网关挡）
- `POST /gateway/draft`、`POST /gateway/note` → `HTTP 401`（两处路由同样真实）
- 对照 `GET /gateway/service/time?query=current` → `HTTP 200 {"time":1793916562}`（公开接口，证明 `/gateway` 前缀本身可通）
- 前端 `_app` chunk（818698 B，带 Referer 才给，否则 403 170 B 桩）里读到：请求路径一律 `'/gateway' + path`；头组装为 `headers:{Token:C, Authorization:"Bearer ".concat(C)}`；`Token` 取自页面 `serverData.Token`，**未登录时该值是空串**
- 422 与 403 的区别要抓准：401/403 是**网关层**（未登录 / CSRF），不是业务参数错误

**修复方案**：①所有业务路径拼在 `/gateway` 之后，网传 `/api/*` 一律不写进代码；②**先 GET 写文章页拿 Token**（`__NEXT_DATA__` 里 `"serverData":{"Token":"…"}`，用整段锚点匹配避免撞同名键），空串即判定「Cookie 不是登录态」并直说——不要带着空 Token 去撞 401；③请求必带 `Origin: https://segmentfault.com` 与 `Referer: https://segmentfault.com/write`，否则先吃 403；④`Token` 与 `Authorization: Bearer` **同值双头**；⑤错误分诊写死：401=未登录/Token 失效、403=CSRF、404=路径变了（明确告诉用户「这是实现要更新，不是 Cookie 问题」）；⑥草稿与发布是**两个不同端点**（`/gateway/draft` 与 `/gateway/article`），不是同一个接口的开关字段，所以 `--draft` 真能存草稿。

**复用配方**：①**同一个路径换个 HTTP 方法从 401 变 403，说明「路由存在 + CSRF 在网关层」**——401/403 语义要先分清再动 Cookie，否则会白排查一整轮；②**Token 可能压根不在 Cookie 里**：先看前端 bundle 怎么组装请求头，再决定要不要新增凭证字段，别为了「填满字段」去编造一个 cookie 名；③页面 HTML 临时抓的 token 要**用整段上下文锚点**匹配并做「空串 = 未登录」判定，只认 `"Token":"` 会在页面结构变化时静默取到错值；④**成功响应形状在没有登录态时是拿不到的**——此时把判据放宽为「HTTP 200 即视为已提交，抠到 id 才打印」，宁少判一次失败，也不要把已发出去的文章报成失败；⑤正文是 HTML 富文本的平台（思否/头条）**图片必须是公网 URL**，本地图走 AtomGit 图床转外链，失败只警告不阻断。

## 22. 头条 7050「保存失败」：不是字段缺失，是 body 编码错了

- 佐证：第三方公开实现（acedata toutiao skill）用 `urllib.parse.urlencode` + `Content-Type: application/x-www-form-urlencoded`，字段仅 `title/content/save/article_ad_type`，走的就是这条通路

**修复方案**：①`buildToutiaoArticleBody`（JSON）整体换成 `buildToutiaoArticleForm`，逐字段 `urlEncodeComponent(k) + "=" + urlEncodeComponent(v)` 拼表单串，复用 `tencent.cj` 里已有的 `urlEncodeComponent`（不重复造）；②请求头改 `application/x-www-form-urlencoded`；③字段集保留实测可用的原 10 个（`save=1` 草稿 / `save=0` 发布、`pgc_id="0"` 新建、`pgc_feed_covers="[]"` 不设封面）；④单测从「JSON 结构断言」改成「form 字段断言」：`save=0`/`save=1`、`pgc_id=0`、`pgc_feed_covers=%5B%5D`、`content=%3Cp%3Ex%3C%2Fp%3E`（尖括号必须转义），并加一条 `startsWith("{") == false` 守住「别再退回 JSON」；⑤`X-CSRFToken` 兜底键名同时修正：本机这串 Cookie 只有 `csrf_session_id`（带下划线），旧代码取 `csrf_sessionid`（少一个下划线）**永远取到空串**，现在按 `csrftoken` → `csrf_session_id` → `passport_csrf_token` 依次取。

**复用配方**：①**同一个报错码下，「换编码」要排在「加字段」之前试**——后台对 body 编码不匹配时常回一个不带字段名的泛化错误码（7050 就是典型），而加字段既改不动根因又污染后续判断；②**对照实验要一次只改一个变量并留铁证**：这轮真正定因的是「同 URL + 同 Cookie + 同正文，JSON→7050 / form→code 0」这一组，其余（Referer/CSRF/额外字段）作为反向排除同步记下来，避免下次重踩；③**先找第三方公开实现看它怎么发**，比自己盲试字段便宜得多——它给出的正是 form 编码这条通路；④form 编码必须对**每个键值都做**百分号转义，HTML 正文里的 `<` `>` `/` `"` 不转义会被服务端当标签/边界解析；⑤`code 0` + `pgc_id` 只是「已写入」，还要回头用 `GET /mp/agw/article/list/?status=all` 回读，确认标题与 pgc_id 都在（`status=draft` 只列**草稿箱**里的历史草稿，`save=1` 建的文章不一定出现在里面，别用它判失败）。

## 23. 头条根本没有「存草稿」这一档：`save=1` 提交即公开发布

**现象**：按社区惯例把 `save=1` 当「存草稿」、`save=0` 当「发布」写了一个多月，工具一直回显「草稿已保存」，用户也一直以为自己发的是草稿。直到查文章状态才发现：那些「草稿」在后台列表里是 `status=3 已发布`，公开页 `https://www.toutiao.com/article/{pgc_id}/` 直接 200 可读——**`--draft` 一直在静默公开发文**。而真正的 `--live`（`save=0`）反而恒回 `7050 保存失败`。

**排查铁证（2026-11-06，同一 Cookie / 同一 URL / 同一份正文）**：
- 只改 `save`：`save=1` → `{"code":0,"message":"提交成功"}` + `pgc_id`；`save=0` → `{"code":7050,"message":"保存失败"}`
- `save=1` 提交后 `GET /mp/agw/article/list/?status=all` 回读该 `pgc_id`：`is_draft=false`、`status=3`、`status_desc=已发布`，`article_url` 是 `https://www.toutiao.com/article/…`（注意 `/item/` 是**老路径，现已 404**，2026-11-06 实测 `/article/<id>/` 200、`/item/<id>/` 404）
- 新建的稿子一开始是 `status=6 审核中`，几分钟后再查自动变 `status=3 已发布`——**审核是自动的，不需要人工点**
- 试「先 `save=1` 建稿，再拿同一 `pgc_id` 用 `save=0` 转正」→ `3014 审核中，无法修改`（补充 `abstract` / `pgc_feed_covers` 同样 `3014`）
- 真草稿接口 `POST /mp/agw/draft/save_ugc_draft`：`draft_type=1` + JSON 与 form 两种编码、加减 `abstract`/`pgc_feed_covers`/`article_ad_type` 共十余组 → **全部 `1066 草稿内容为空`**
- 对照组：后台真实「草稿箱」里的历史稿件是 `status=1 / is_draft=true`，说明「草稿」这个状态客观存在，只是**发文接口不提供写入它的通道**

**修复方案**：①`--live` 改走 `save=1`（唯一能真正发布的通道），成功文案从「发布成功」改为「已提交」并说明会进审核队列；②`--draft` **整段不提交**——在函数入口直接返回，打印原因与「要真发请加 `--live`」，把不可逆动作的选择权交回用户；③同步改掉 usage、`doctor` 提示、模式回显三处「`--draft` = save=1 存草稿」的错误说明；④删掉失去调用方的 `toutiaoDraftUrl`（连带其单测断言），保住 `cjpm build` 零警告。

**补充矩阵（2026-11-06 拿到真实编辑器抓包后复验，补齐上一轮的空白）**：

| `save` | 回执 | 后台落点 |
| --- | --- | --- |
| `0` | `7050 保存失败` | 无（编辑器「点发布」档，需浏览器风控签名） |
| `1` | `code 0` + `pgc_id` | `status=6 审核中` → `status=3 已发布` |
| `2` | `5009 发布失败，请重试` | 无 |
| `3` / `4` | `code 0` + `pgc_id` | 同 `save=1`，也是提交并发布 |

三条定因：
- **`save=0` 的 7050 不是字段缺失**：按抓包形态带齐 25 个编辑器字段（`source=29`/`extra`/`title_id`/
  `mp_editor_stat`/`draft_form_data`/`search_creation_info`/`praise`/`timer_status`…）+ 真实草稿 `pgc_id`
  仍回 `7050`；再原样补上 `msToken`/`a_bogus`（URL）与 `tt-anti-token`/`x-secsdk-csrf-token`（头）
  **仍是 `7050`**——这些都是 webmssdk 的一次性风控产物，重放即失效。结论：`save=0` 脚本无法复现，
  与「字段不全」无关，别再往加字段方向排查。
- **真草稿箱客观存在，但没有脚本写入通道**：`GET /mp/agw/creator_center/draft_list?type=0&count=20&app_id=1231`
  回 `{"code":0,"draft_list":[…17 条…]}`（字段 `gid` 即 `pgc_id`、`draft_type=2`、`rich_title`/`graphic_extra`），
  `GET /mp/agw/article/edit?pgc_id=<id>&wxstyle=0&format=json` 能读回完整草稿正文；这 17 条**全部由编辑器
  自动保存产生**。判草稿要看这个接口或文章列表的 `status=1 草稿`，`status=all` 的列表里草稿与已发布是混排的。
- **`save_ugc_draft` 两个方向都堵**：`draft_type=1` → `1066 草稿内容为空`（`content`/`article_content`/
  `draft_content`/`graphic_content`/`content_html`/`body` 六个键名全试过），`draft_type=2` → `1064 草稿类型参数错误`。

**复用配方**：①**「保存」与「发布」在中文后台里不是靠参数区分，而可能只差这一次提交**——凡把某平台的 `--draft` 当安全档，必须先用后台列表回读 `status`/`is_draft` 求证，别看接口返回的 `message`（它写的是「提交成功」，什么都没承诺）；②**错误码与语义要成对留证**：这次能定案靠的是「`save=1` → status 3 已发布」和「`save=0` → 7050」两点同时成立，单看任何一个都会得出错误结论；③**没有草稿通道时，宁可少一个功能**：静默把草稿发到公网是用户最难原谅的一类 bug，直接拒绝提交 + 打印原因，比「尽力而为地发出去」正确得多；④**改语义后要全仓搜一遍旧文案**（usage / doctor / 回显 / CHANGELOG / 文档），否则代码对了、提示还在骗人。

## 24. 头条图床 1050「图片上传失败」：既可能瞬时抖动，也可能是图片编码；扁平响应里 `state` 是空串

**现象**：同一篇 6 图文章连续发布，每次失败的图都不一样（一轮 1/6 失败、下一轮 3/6、再一轮 2/3），有时又全过。
失败回 `{"code":1050,"message":"图片上传失败"}`。更怪的是：有的图 HTTP 200、`code` 也不是 1050，脚本却仍报「上传失败」。

**排查铁证**：
- 单张重传实验：同一张图第一次 1050、第二次 `code:0` + `web_uri`，图床直链可用 → 1050 不是稳定拒绝。
- 成功响应体是**扁平结构**（无 `data` 包裹），成功时 `state` 字段**常为空串**；脚本原判据是
  `state == "SUCCESS"`（旧版 ueditor 协议的形状），于是「`code:0` 的成功」被判成失败并打印失败。
- `x-requested-with: XMLHttpRequest` 漏带必回 1050（稳定复现），与随机失败是两个不同成因，别混为一谈。

**修复方案**：①成功判据改为 `code == "0"` **或** `state == "SUCCESS"`（两种协议都认）；
②单张最多重传 2 次（`TOUTIAO_UPLOAD_MAX_ATTEMPTS`），每次间隔 1s；
③可重试判据抽成纯函数 `toutiaoUploadRetryable(code, status)` 便于单测：`1050`/`5009`、HTTP 5xx/429/0、
以及「200 但响应不可解析」算瞬时；`1000`/`100004`/`100005`（未登录）与 `7115`（正文图链非法）立即失败不重传。

**复用配方**：①**同一批请求里失败集合每次都变 = 抖动，不是契约**——这时该加重传，而不是去翻文档找参数；
②判成功优先认业务码，别只认某个字符串字段：字段可能是旧协议的残留，空串会把成功判成失败；
③重传要有白名单：未登录/参数类错误重传只是浪费时间和额度，先判「重传是否可能改变结果」再决定重试。

**补充（2026-11-08，换了一篇配图文章后又踩到）**：1050 还有一个**确定性**成因——图片**编码格式**被拒。
同一批 5 张图里，`cjt-dist-size.png`（rsvg 导出的 8-bit **RGBA**，带 alpha 通道）连续 3 次 1050；
`cjt-vs-tauri.png`（16-bit/color RGB）同样稳定被拒；其余 8-bit RGB 图全部稳定 `code:0`。
用 `convert in.png -alpha off -depth 8 -type TrueColor PNG24:out.png` 转成 8-bit RGB 后**一次通过**。
所以「重传能变好」只对抖动成立：**同一张图每次都被 1050 拒 = 格式问题，改图比加次数快**。
`uploadToutiaoImage` 现在在 1050 重试耗尽时直接打印这条排查提示，不让用户误以为只是限流。

## 25. 图片转存没全成功就照发 = 白烧发文额度

**现象**：头条那轮 6 张图只有 3 张进了头条 CDN，`publish` 仍照常提交，服务端回 `7115 图片uri非法`，
整篇拒稿；而头条单账号每天约 4 篇额度，这次拒稿把当天的额度实打实消耗了一次。腾讯云、CSDN 上也有
同类浪费（分别白踩一次 `400300012` 限额与一次参数修订重试）。

**排查铁证**：转存函数返回 `(html, ok, fail)` 三元组，`fail=2` 时旧代码只 `println("警告：…")` 然后继续提交；
同一篇文章删掉这三张图后立刻发布成功，说明拒稿原因就是那两张没进 CDN 的图（非标题、非格式）。

**修复方案**：新增 `rehostFailGate(platform, failCount, force)`（纯函数 + 单测），`fail > 0` 默认**中止发布**并给
三条出路（重跑 / 删图 / 显式 `--force`），`--force` 才继续。CSDN 侧仍保留 `CSPUB_STRICT_IMAGES=1` 的强校验语义。

**复用配方**：①**「best-effort」只适合可回滚、无代价的通道**——发文有每日额度、拒稿还带一次性成本，
这类链路必须 fail-fast，让用户当场决定，不要在失败状态下帮他把额度花掉；
②把「要不要强行继续」做成显式开关（`--force`）而不是默认行为，日志里同时打印「继续的代价」；
③门禁函数保持纯函数（`force` 由调用方传），这样不用联网也能写单测覆盖三种分支。

## 26. 「图片转存全失败」可能两个原因一起发生：图源被 WAF 拦 + 转存方是服务端抓链

**现象**：v0.3.1 真机发腾讯云草稿，`图片（腾讯云图床）：成功 0，失败 6`，6 张图全部保留原链接；
但同一批图在实战当天是**全部成功**转存过的。

**排查铁证**：
- 直接 curl 图源：`https://raw.gitcode.com/qq8864/images/raw/main/cjh/embed-arch.png` → `HTTP 418 / 3223 bytes`
  （CloudWAF 挑战页）；同图换 `https://api.gitcode.com/api/v5/repos/qq8864/images/raw/cjh/embed-arch.png?ref=main`
  → `HTTP 200 / 286732 bytes`。**图源是本机的锅，不是图床挂了。**
- 只改本机下载（`downloadImage` 加备用端点回退）后重发：**仍是 0/6**。说明这条路根本没走本机下载。
- 读代码确认：腾讯云转存是 `SaveHttpImageCommon` RPC，payload **只有 `url`**，由**腾讯云服务端**去抓这个链接
  ——本机的下载能力与它无关。把交给它的 URL 先换成 api 端点后再发：`成功 6，失败 0`（草稿 `draftId 342313`）。

**修复方案**：`atomgitApiFallbackUrl(url)` 做 raw→api 端点换算（纯函数 + 单测，段数不对/非 raw 形状返回空串），
两个消费方各自接：①本机下载 `downloadImageTry` 失败后回退一次；②腾讯云 `rehostTencentImages` 在**交出 URL 之前**
就换成备用端点。

**复用配方**：①**「本机能下载」≠「平台能取到」**——转存要么本机下载后上传（CSDN/头条），要么把 URL 交给平台抓
（腾讯云），排查前先确认是哪一种，只有前者能靠本机回退救；
②同一个外链域名的可用性要按**消费方**分别验证：raw.gitcode.com 对 WAF/服务端抓取都不友好，api 端点两边都通，
所以「把 URL 换成能用的那个」才是完整修法；
③`Success 0 / Fail N` 这种全量失败几乎总能归到「入口不通」而不是「逐张处理逻辑有 bug」——先 curl 一遍入口，省半天。

## 27. 头条转存「5 张全部读不到图片」：URL 里的 `&` 已被渲染成 `&amp;`

**现象**：一篇 5 图文章发头条，转存阶段 5 张全部打印「⚠ 读不到图片（头条会拒稿 7115）」，
但那些链接浏览器直接打开是好的、`curl` 也回 200。

**排查铁证**：每条告警里的链接长这样——
`https://image-tt-private.toutiao.com/...~tplv-obj.image?lk3s=...&amp;policy=...&amp;x-orig-sign=...`，
参数分隔符是 `&amp;` 而不是 `&`。发出去这个串，签名参数名就成了 `amp;policy`，服务端按无效签名拒绝。
根因：`rehostToutiaoImages` 处理的是 `mdToHtml` **渲染后的 HTML**，渲染时 `&` 已被转义成 `&amp;`；
而 `collectImgSrcs` 直接取 `src` 原文去下载。头条自家 CDN 的图（签名链带三个 `&`）是重灾区。
其他平台没暴露，是因为 CSDN/知乎/掘金的转存读的是 **Markdown 原文**里的 URL，没经过 HTML 转义。

**修复方案**：新增纯函数 `htmlUnescape`（`util.cj`，覆盖 `&amp; &lt; &gt; &quot; &#39; &apos;`，
只反转义一层、未知实体原样保留、分段 append 整段 UTF-8 不拆汉字），
`rehostToutiaoImages` 在**下载与取扩展名**时用反转义后的 URL；
`map` 的 key 仍保留 HTML 原文串——因为 `rewriteHtmlImgs` 要拿正文里的原 `src` 去匹配回写。

**复用配方**：①**「在 HTML 层做字符串处理」必须先确定这一层有没有被转义过**，取 URL、取路径、
算长度都算在内；②同一个函数里如果既有「按原文匹配」又有「按语义使用」，就把两种取值分开命名
（`u` 与 `fetchUrl`），别指望一个变量两头都对；③告警里打出来的 URL 要能被直接复制去 curl——
这次正是因为打印的就是坏串，才一秒钟看出 `&amp;`。

## 28. 百家号：封面只能取「正文首张本地图」，而正文里的本地图根本不会被上传

**现象**：为了让百家号有封面，按预检提示在正文放了一张本地图 `docs/imgs/cjt-vs-tauri.png`，
封面确实上传成功了；但那篇文章**正文里那第一张图是空图/死链**——`src` 是本地相对路径，
网页上解析成站点自己的路径。

**排查铁证**：读伴生脚本 `scripts/baijiahao_publish.py`，它只有 `--cover-file` 一个图片入口
（`finput.set_input_files(args.cover_file)` → 上传封面），**不处理正文 HTML 里的 `<img>`**；
而 `publishToBaijiahaoCookie` 的封面来源被写死成「正文第一张非 http 开头的图」。
于是形成一个死角：正文全用外链 → 没有本地图 → 无封面被拒；正文放本地图 → 有封面 → 那张图死链。

**修复方案**：`publish --cover <本地图>` 显式指定封面，与正文图解耦（正文可以全用公网直链）。
`platformCheckIssues` 增加 `coverGiven` 参数：给了 `--cover` 就不再要求正文含本地图；
本地图告警在百家号下改成**准确描述**（「百家号只上传封面、不上传正文图，正文里的本地图会死链」），
不再误导成「配 `CSPUB_ATOMGIT_TOKEN` 就好」。`check` 命令同样接受 `--cover` 以便预检口径一致。

**复用配方**：①**预检规则别只报「不满足」，要报「怎么满足才不出副作用」**——原来那条提示照做就会埋一张死链图；
②「A 能力依赖 B 的数据」时，优先给 A 加独立入口，而不是逼 B 的数据反过来迁就 A；
③官方接口与伴生脚本两条通道能力不等价（token 通道封面走 `cover_images` URL，脚本通道走本地文件），
新参数要写明适用哪条通道，别让用户以为到处都能用。
