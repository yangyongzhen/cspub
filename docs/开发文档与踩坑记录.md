# cspub 开发文档与踩坑记录

> 条目格式：现象 → 排查铁证 → 修复方案 → 复用配方。只收实测验证过的条目。

## 1. OBS 上传返回"HTTP 200 + 0 字节"空图

**现象**：图片转存链路走通（签名接口返回正常、OBS 上传返回 200），但图床直链打开是 0 字节空文件，正文图裂。

**排查铁证**：CSDN 图床签名接口响应里 `customParam.isAudit` 字段是 **JSON 数字**（如 `"isAudit":1`），而 cspub 最初用只认字符串的 `jsonStr` 取值，取到空串；把空的 `x:isAudit` 表单字段发给华为 OBS multipart，OBS 接受请求（200）但生成的对象是 0 字节。表象完全像"请求被网关吞了"，实际是签名回调字段没取到。

**修复方案**：新增 `jsonScalar`（util.cj）——按 JsonKind 分派取值（字符串/数字/布尔字面量各走各路），`x:isAudit` 固定给 `"1"`。

**复用配方**：对 CSDN/华为 OBS 这类"前端烙死"的接口，**取 JSON 字段永远按 Kind 取，不要假设类型**；调试上传类接口时，先核对"签名响应里每个字段的实际 JSON 类型"，再核对"OBS 收到的每个表单字段值"。

## 2. CSDN 防盗链的真面目：HTTP 200 + 0 字节

**现象**：站外图 `<img>` 直连，状态码 200 看似正常，图片不显示。

**排查铁证**：`curl` 拉外链图返回 200 但 body 0 字节；同一 URL 换 UA/Referer 依旧。结论：CSDN 在网关层剥掉站外图响应体，常规"URL 有效性检查"手段全部失效。

**修复方案**：唯一解法是把图转存为站内图（csdnimg.cn 直链）。cspub 的转存流水线：扫描（代码围栏内跳过）→ 分流（内网/回环拦截、CSDN 图床/data: 跳过）→ 下载（拒绝 30x、单张 12 MiB 上限）→ 图床签名上传 → 从后往前回写（防偏移挪位）→ best-effort 不阻断发文。

**复用配方**：任何"发到 CSDN 的内容里带图"的需求，都必须走转存，不要赌外链；处理图片引用时，代码围栏内的 `![]()` 是示例文本，必须跳过。

## 3. TLS 信任：CSDN 证书链过不了 stdx 校验

**现象**：`https://blog.csdn.net` 的请求在 stdx TLS 下报 unknown CA；本机 1.0.5.1 与 1.2.0.1 两代 stdx、默认模式与 CustomCA 模式（内嵌逐字节一致的 Certum 根）全报；而系统 curl 验同一条链通过。

**排查铁证**：同一证书链，curl OK / stdx NG；CustomCA 内嵌根与链根逐字节一致仍 NG → 排除"根没带对"，指向 stdx 动态加载的 OpenSSL 验证行为问题（已记录待查，非本工具可修）。

**修复方案**：`--insecure`（TrustAll）作为显式逃生口。**正式发文先试默认模式，失败再加 `--insecure`**——HTTPS 内容仍加密，只是不验服务器身份，风险自担；不要默认带上。

**复用配方**：遇到"curl 过、stdx 不过"的证书问题，先对比两者加载的 OpenSSL 与信任来源，再考虑 TrustAll 逃生口；不要徒劳地反复换根证书。

## 4. stdx 1.2.0 的 TLS API 编译差异

**现象**：stdx 升到 1.2.0.1 后编译不过。

**排查铁证**：三处——① `CertificateVerifyMode` 移到 `stdx.net.tls.common` 子包；② 变体要求限定名（`CertificateVerifyMode.TrustAll`）；③ `CustomCA` 收 `Array<Certificate>`（接口），而 `X509Certificate.decodeFromPem` 返回 `Array<X509Certificate>`（类），Array 不协变。

**修复方案**：显式 `import stdx.net.tls.common.*`；变体写限定名；接口数组显式逐元素搬移（`for` 循环 append，不要强转）。

**复用配方**：stdx 大版本升级先看 TLS 子包结构变化；接口数组 vs 类数组的协变问题统一用显式循环搬移解决。源码以 1.2.0 为准，1.0.5.1 下这几处编译不过。

## 5. UTF-8 字节语义：汉字别按字节切

**现象**：摘要截断后出现乱码；行内渲染后部分汉字变非法序列。

**排查铁证**：截断点落在多字节序列中间；逐字节 `append` 把 3 字节汉字拆开。

**修复方案**：截断按首字节判界（`(b & 0xC0) != 0x80` 回退到边界）；行内渲染按区间整体转码（`Utf8View`/区间切片），不逐字节 append。

**复用配方**：仓颉里 String 的 `text[i]` 是 Byte——**凡是"按字符处理中文"的场景，一律按 UTF-8 边界切**。

## 6. 本机构建运行缺 stdx 动态库

**现象**：直接执行 `target/release/bin/main` 报 `error while loading shared libraries: libstdx.encoding.json.so`。

**排查铁证**：产物动态链接 stdx（cjpm.toml 未走静态段），运行时找不到 stdx so。

**修复方案**：
```bash
export LD_LIBRARY_PATH=<stdx>/dynamic/stdx:<cangjie>/runtime/lib/linux_x86_64_cjnative:<cangjie>/third_party/llvm/lib
```

**复用配方**：先补 LD_LIBRARY_PATH 再怀疑构建；发布产物（dist/ 包）不含此问题——打包时静态链接或在包内附 runtime 说明。

## 7. 百家号纯 Cookie HTTP 发文走不通（React 事件链）

**现象**：拿浏览器 Cookie 直调百家号发布接口 `/rest/2.0/elite/article/publish`，稳定返回 HTTP 500；`builderinner` 官方接口要 `app_id`+`app_token`，而开发者入口 2026 年起是定向邀请制，普通账号后台没有「开发」菜单。

**排查铁证**：①baijiahao-auto skill（2026-04 实战）记录发布按钮是 React SPA 组件，点击需经 `preCheck→paramProxy→re()` 完整事件链——连 CDP 代理的原生 `click()` 都只能触发"保存草稿"，触发不了发布（已知限制 #5）；直调 API 缺 CSRF token 等完整参数必 500（#12）。②社区所有可用实现（baijiahao-publisher、opub、omnipost、PostFlow）无一例外走 Playwright 浏览器自动化，没有一个纯 HTTP 发布成功先例；连编辑器"存草稿"的 HTTP 端点都没有公开可用记录。

**修复方案**：cspub 的百家号做双通道——有开发者凭证走官方 token 接口（`src/baijiahao.cj`）；否则 Cookie 走浏览器自动化伴生脚本 `scripts/baijiahao_publish.py`（Playwright：Cookie 注入 → `builder/rc/edit?type=news` → 关 `.cheetah-tour` 弹窗 → `input.cheetah-input` 上 execCommand 填标题 → `#ueditor_0` iframe 里 `editor.setContent` + `fireEvent('contentchange')` + `sync()` → 点「存草稿/发布」）。凭证经临时文件传给子进程，用完即删。

**复用配方**：凡是"React 后台 + 无公开 API"的平台（百家号/小红书/快手同款），别在纯 HTTP 上耗时间，直接浏览器自动化；标题受控组件用 execCommand、UEditor 改内容后必须 fireEvent+sync，这两个选择器/姿势是社区实测可复用的。

## 8. 百家号新版编辑器是 Lexical：选择器/注入姿势全变

**现象**：按社区旧配方（`input.cheetah-input` 填标题、UEditor iframe `setContent` 填正文）自动化百家号编辑页，标题框等不到、正文填不进；偶发正文内容整段出现在标题框（超 86/64 限制）。

**排查铁证**：①编辑区 DOM 带 `data-lexical-editor="true"`——新版换成了 Meta Lexical 框架，`execCommand`/合成 ClipboardEvent 一概不生效；②标题与正文是**两个同名 class 的 Lexical 编辑器**，`querySelector` 取第一条匹配拿到的是标题框——"正文贴进标题（86/64）"就是这条；③headless 下 `navigator.clipboard.write` + Ctrl+V 也不触发 Lexical 粘贴，**逐字键入（keyboard.insert_text，真实 beforeinput）实测可靠**；④`「确定 (1)」`按钮文案带计数，`get_by_text(exact=True)` 匹配落空；⑤AI 推广弹窗/「新增智能标题」气泡/已关闭弹窗的空 `.cheetah-modal-wrap` 时序不定地拦截点击，Playwright click 反复 retry。

**修复方案**（`scripts/baijiahao_publish.py`）：标题= `[data-testid='news-title-input'] [data-lexical-editor='true']`，正文=**不在标题框里**的 `data-lexical-editor`（`findIndex + closest` 区分）；二者都用 `keyboard.insert_text` 键入（正文为 `_plain(html)` 纯文本，富文本格式放弃）；键入后校验 innerText，失败重试 3 次 + DOM 直写兜底；每步前循环关弹窗（DOM click `button.close` + 含「立即体验」的包裹层整层隐藏 + 空包裹层去指针化）；发布走「选择封面」对话框 `input[type=file]` `set_input_files` 上传本地图，确认按钮用 `button:has-text('确定')` 包含匹配；成功判据必须校验标题与正文字数双非空，防空内容假成功。

**复用配方**：遇到 Lexical 编辑器（认 `data-lexical-editor` 属性）直接放弃合成事件路线，用真实键盘输入 + 点击后校验回读；同名 class 的多编辑器页面用 `closest(容器)` 区分而不是取 first；浮层拦截一律「JS 隐藏 + force click + 结果回读」三件套。

## 9. 掘金 ImageX 图片上传：直调签名必然被拒，改走真实浏览器通道

**现象**：掘金把正文相对路径图片渲染成 `https://juejin.cn/<路径>` 死链；转存需走字节 ImageX 五步链，但 `ApplyImageUpload` 稳定返回 `SignatureDoesNotMatch`（CodeN 100010）——同一份实现（Python 与仓颉签名逐字节对账一致）时而被接受、时而被拒，最终演变为长期被拒。

**排查铁证**：①旧接口 `/images_upload/v1/create` 已 404 下线，现行五步链配方来自 juejin-skills/mukun_md_push 社区逆向；②仓颉签名 == Python 签名（同输入逐字节一致），排除本地算法差异；③**浏览器抓包（决定性）**：在掘金编辑器里真实上传一张图，拦住发往 `imagex.bytedanceapi.com` 的 ApplyImageUpload，其 `SignedHeaders` 只有 `x-amz-date;x-amz-security-token`（**不含 host**），query 原序为 `Action,Version,ServiceId`（非字母序）；照抄这套组合重放仍被拒（详见④）；④**排除法穷举**：字母序/原序、带/不带 host、GET/POST、签不签 `x-amz-content-sha256`、sk 是否 base64 解码、`AWS4` 前缀有无、火山原生 `HMAC-SHA256` 变体，10+ 组合**全部** `SignatureDoesNotMatch`；而**同一时刻同一浏览器的上传一次成功** → 结论：网关按**客户端 TLS/UA 指纹**校验，不看签名内容本身；⑤旁证：`Credential` 的 scope 用令牌内 `LTAccessKeyId` 会改报 `CheckAuthenticationError`，用 `AccessKeyId` 才推进到签名比对 → AK 本身正确，问题只在「谁来发这个请求」；⑥gen_token 的 GET 带 `Content-Type` 会签发坏令牌（社区同款注释），属另一独立坑。

**修复方案**（`src/juejin.cj` + `scripts/juejin_upload.py`）：**主通道改为真实浏览器上传** —— playwright 携带 Cookie 打开 `https://juejin.cn/editor/drafts/new`，对每张本地图调用 file input 的 `set_input_files`，拦 `get_img_url` 响应取 `data.main_url`（即编辑器自己会写进正文的同一条地址），逐图输出路径→URL 映射 JSON；仓颉侧 `rehostJuejinImages` 优先调该脚本、脚本缺失时降级内置 `uploadJuejinImage`（ImageX 五步链 + CRC32 表 + SigV4）。gen_token/get_img_url 只带 UA+Cookie；Commit best-effort；单张失败保留原链接并提示，不阻断发文。

**复用配方**：①「AWS 签名逐字节一致却被拒」时，先抓浏览器真实请求对照 `SignedHeaders`/query 序，再穷举变体；**若真实浏览器能过而非浏览器客户端全灭，直接判为指纹校验，别再改签名**——换浏览器通道（playwright + Cookie + 拦响应取结果）是成本最低的解法，与百家号伴生脚本同一模式；②掘金编辑器上传后图片地址由 `get_img_url` 下发，直接取 `data.main_url` 即可，无需自己拼；③**该 CDN 直链对 `curl` 一律 403**（边缘返回 `TLB` 错误页，拦非浏览器客户端），验收必须用浏览器内 `img.naturalWidth > 0` 判定，别用 curl 状态码误判成「图片坏了」；④五步链固定形状备查：gen_token 只带 UA+Cookie、直传必须带 `Content-CRC32`（缺了报 4007）、`get_img_url` 参数名是 `uri`。

## 10. 掘金其实认外链：图片不必搬进平台图床

**现象**：按第 9 节的结论，掘金正文的本地图片只有两条路——浏览器通道（依赖 `python3 + playwright + chromium`）或直调 ImageX（被指纹校验拒死）。整条链路又重又脆，跑一篇要拉起一个浏览器。

**排查铁证**：①**样本反证平台并不限制外链**——`https://juejin.cn/post/7704394460696461350` 正文 3 张图全部是 AtomGit 仓库链接（`atomgit.com/api/v5/repos/qq8864/cj-tauri/raw/...?ref=main`），浏览器渲染 `loaded=True`；②**复验要走自己的发布通道**（编辑器手写与 API 建草稿是两条路径，不能只看别人的文章）：`cspub publish` 以 `article_draft/create` 建草稿 `7704389851194605594`，正文只放一条外链图，浏览器打开该草稿 → `loaded=True 3120x2080`，正文采样里就是 `![外链图](https://atomgit.com/api/v5/...)`；③**外链可匿名直取**：`.../qq8864/images/raw/cjh/arch-diagram.png?ref=main` → `HTTP 200`、`content-type: image/jpeg`、210777 字节，无需 Cookie/Referer。→ 平台图床只是「编辑器顺手自动上传」的默认行为，**不是渲染的前置条件**。

**修复方案**（`src/atomgit.cj` + `src/juejin.cj`）：掘金图片改三级降级——①**外链优先**：配了 `CSPUB_ATOMGIT_TOKEN` 就把本地图逐张 `POST /api/v5/repos/{owner}/{repo}/contents/{path}`（base64 内容 + 提交说明 + 分支），正文回写 `https://atomgit.com/api/v5/repos/{owner}/{repo}/raw/{path}?ref={branch}`；②①失败的图降级伴生脚本浏览器通道；③再降级内置 ImageX；三级都不成则保留原引用并提示，**best-effort 不阻断发文**。默认仓库 `qq8864/images`、分支 `main`、目录 `cspub`，可用 `CSPUB_ATOMGIT_REPO/BRANCH/DIR` 覆盖；令牌走 `Authorization: Bearer` 头，不落 URL。

**复用配方**：①**判断平台是否限制外链，别查文档也别看别人文章了事**——拿一条真实外链图走自己的发布通道（API 建草稿）再以浏览器内 `naturalWidth>0` 判定，因为「编辑器手写」和「API 写入正文」是两条渲染路径；②图床选型优先复用**自己已有的存储**（代码托管的 raw 链接），省掉整套平台图床签名链与浏览器依赖；③AtomGit 新建文件用**随机文件名**避坑——`contents` 对已存在路径返回 400，新建接口不复用旧文件，重名就得上 PUT 带 blob sha；④AtomGit 鉴权三种方式等价（`Authorization: Bearer` / `PRIVATE-TOKEN` / `access_token` 查询参数），选头方式，查询参数会把令牌留在 URL 里；⑤**仓颉块注释支持嵌套**：注释正文里写了 `image/*` 这种含 `/*` 的字样会再开一层注释，报 `unterminated block comment`——注释里别出现 `/*`。

## 11. 开源中国：官方 OpenAPI 走不通，站点自用 apiv1 + 自带图床才行

**现象**：要给开源中国（oschina.net）加发文通道，官方路线全线不可用——`/action/openapi/blog_pub` 要先注册应用拿 `client_id`/`client_secret`，再走 oauth2 换 `access_token`（授权范围还要 `password`），个人自用根本落不了地。退而直接打站点自己的 `apiv1.oschina.net`，带着浏览器登录后的 `oscid` Cookie 请求 `user/myDetails`，却被回 `{"code":40001,"message":"用户未登录，请先登录"}`（HTTP 200），看起来 Cookie 完全不认。

**排查铁证**：①**端点从编辑器 bundle 反查**：`www.oschina.net/blog/new` 只返回 3730 字节 SPA 外壳，必须在 `static.oschina.net/oschina/space/v2/js/` 的 `draftWriteType-*`/`create-*` chunk 里扒请求体——`I("/blog/web/add",c)` 的 `c` 里有 `title/content/contentType/type/catalog/privacy/disableComment/draft/user/isAiRelated`，草稿走 `"/api/draft/save_draft"`（同一个 `u` 对象但不带 draft/type），分类走 `"/blog_catalog/list_by_user"`；②**40001 是我自己的锅**：`cookie_kaiyuan` 文件里存的**已经是 `oscid=ESvQB0…` 整串**，我又按 `-b "oscid=$CK"` 拼了一次，服务端收到 `oscid=oscid=…` 自然认不出登录态；改成 `-H "Cookie: $(cat cookie_kaiyuan)"` 透传后同一端点立刻返回 `success:true` + `result.userId=4197674`，分类 `list_by_user` 也同步通了；③**图床端点靠探测**：候选路径里只有 `/oschinapi/upload/img` 返回 200（其余 `/upload/image`、`/file/upload`、`/api/image/upload` 全是 Spring 的 404 结构体），multipart 字段名 `file`，2MB 图片单请求即成功；④**直链「看着像坏的」其实好的**：返回 `https://oscimg.oschina.net//null/up-<md5>.png` 带着一段 `//null/`，裸 `curl` 取它得 403（146 字节 `TLB` 页、`text/html`）——换成浏览器 UA + `Referer: https://www.oschina.net/` 再取 → `HTTP 200`、`content-type: image/png`、130318 字节，与源图**逐字节一致**；⑤**草稿回读闭环**：`GET /api/draft/edit/detail?id=<draftId>`（query 传 id；改成 POST JSON 会回「草稿不存在」code 500）能拉回正文，看到图片已被回写成图床直链、Markdown 原样保留。

**修复方案**（`src/oschina.cj` + `src/main.cj`）：新增 `--platform oschina`——鉴权只透传 `oscid` 整串 Cookie，请求固定带 `Referer`/`Origin: https://www.oschina.net`；`userId` 缺配置时先 `GET /user/myDetails` 现查；分类按 `front-matter categories` 名匹配、匹配不到取账号第一个（也可 `CSPUB_OSCHINA_CATALOG` 直指）；正文以 `contentType: 1`（Markdown）原样提交，**不要预渲染 HTML**；图片优先级 = **平台自带图床 `/upload/img`（有 Cookie 就能用）→ AtomGit 外链兜底 → 保留原引用**，仍 best-effort 不阻断发文；成功判据 `code == 200` 且拿到 id（草稿 `result.id`、发布 `result` 标量）。

**复用配方**：①**本地 cookie 文件先看清是不是自带 `name=` 前缀**——`-b "oscid=$(cat file)"` 这种二次拼接会得到 `oscid=oscid=…`，服务端一律当未登录（408/40001 类错误先怀疑这一步，别怀疑 Cookie 失效）；②平台的「官方开放 API」要注册应用 + oauth2 时，直接反查它**自己前端调的内部 apiv1**（同 Cookie 同鉴权，请求头补齐 `Referer`/`Origin` 即可通），成本低一个数量级；③`static.*` 的 JS chunk 请求要带浏览器 UA + `Referer`，否则 CDN 直接 403，扒包时先补齐这两个头；④直链里出现 `/null/`、双斜杠别急着判死链——**验收一律带浏览器 UA 取回并和源图比字节**，无 UA 的 403 是 CDN 拦客户端，不是对象不存在；⑤同一平台「草稿」和「发布」常是两个端点、两种 `result` 形状（对象 `.id` vs 标量 id），解析函数要两者都吃；⑥`privacy` 这类布尔字段的语义别靠猜——语义没实测确认前做成可配置项并写清默认值，别把该公开的文章默默发成私密（或反过来）。

## 12. 发布接口回了 id ≠ 文章已公开：SPA 外壳与审核态

**现象**：开源中国 `--live` 正式发布一路绿灯——`/blog/web/add` 返回 `code: 200` + 博客 id `19787222`，`blog/detail` 也能读到完整正文与图片，但用户在浏览器打开的地址是「找不到您访问的页面」。更迷惑的是：同一地址 `curl` 永远拿到 `HTTP 200`，看上去「文章好好的」。

**排查铁证**：①**先怀疑自己拼的 URL**：原实现输出 `https://www.oschina.net/u/4197674/blog/19787222`，实测**服务端 404**（1548 字节错误页），而 `https://www.oschina.net/blog/19787222` 回 200——但把 id 改成不存在的 `999999999` 或写错一位的 `1978722`，返回**同样是 200 + 3730 字节**，说明这是 SPA 外壳路由（任何 id 都回同一份外壳），**状态码根本不能判活**；②**改判据为浏览器渲染**：playwright 打开 `https://www.oschina.net/blog/19787222`，`document.title` 是「找不到您访问的页面」、正文长度 113、`oscimg` 图 0 张——带登录 Cookie 再渲染结果一致，排除「游客不可见但自己可见」；③**内容确实已入库**：`GET /oschinapi/blog/detail?id=19787222` 回 `code:200`，`contentType=1`、`catalog=6616684`、正文是服务端渲染后的 HTML（`<h2>/<p>`），3 张图已是 `oscimg.oschina.net//null/up-<md5>.png` 且三张直链均 200、617773/705372/259509 字节与源图**逐字节一致**；④`ident` 字段为 `null`（未生成 slug）、`folder=99`——推断为**新号/首篇走人工审核**，发布即入库、审核通过才公开。

**修复方案**：①`oschinaArticleUrl` 改为 `${OSCHINA_SITE}/blog/{id}`（去掉 `userId` 参数，单测断言同步改）；②CLI 输出与 README 明确「发布成功≠立刻公开」，提示审核态需稍后复验；③验收流程固定为「接口取正文与图 → 浏览器渲染判标题/正文长度/图 `naturalWidth`」，不再用 `curl` 状态码当凭证。

**复用配方**：①**现代 SPA 站点的 200 毫无信息量**——路由外壳对任意 id 都回 200，判「文章/资源是否存在、是否公开」必须用浏览器渲染（`document.title`、`body.innerText` 长度、`img.naturalWidth`）或调后端详情接口；②发布类接口返回 id 只证明「写入成功」，**公开可见性要单独验一层**（新号、首篇、含外链/敏感词都可能触发审核），别把 id 当上线凭证；③同一平台的「详情路由」和「列表/详情接口」往往两套 id 语义（数字 id vs slug `ident`），`ident` 为 null 常意味着尚未走完发布/审核流程；④文档与 CHANGELOG 里对未闭环的验证要**明写「待确认」并留下复验方法**，别把「接口 200」写成「已上线」。

## 13. 图片转存全失败会静默发出死链文，`imgs` 预演还帮着骗人

**现象**：掘金首发（`7704603488899366939`）5 张图全部转存失败，CLI 打了 5 行 `⚠ 掘金图片转存失败（保留原引用，网页上会显示死链）` 加一行 `图片转存：5 张待转，成功 0，失败 5`，然后**照常把草稿建完**，线上文章五张图全是裂图。排查时先用 `cspub imgs` 预演，输出却是 `skip (not http)`，看着像「这些图本来就不用转存」，进一步把人带偏。

**排查铁证**：①`rehostImages`（`src/images.cj` 本地路径分支）对非 http 引用走的是「读本地文件 → 上传图床」，实际会传，与 `imgs` 的 `skip (not http)` 标签直接矛盾——标签只判「是不是 http」，不认本地绝对路径；②同一批文件两处结论相反：旧二进制的 `imgs` 输出 5 条 `skip (not http)`，而发布日志同时打出「掘金：上传正文图片 5 张」；③真正决定「发出去会不会裂图」的判据是**转存后的正文**里还有没有非 http 引用（`hasLocalImages`），而当时只有开源中国一条链路调了它，其余四个平台没人管；④失败计数打了一行字不等于用户收到告警——五个平台各打各的计数，没有统一收口。

**修复方案**：①`imgPreviewAction`（`src/images.cj`）把预演标签纯函数化：本地绝对路径 → `upload (local file)`，`imgs` 与真实发布共用同一份判定；②`localImageCount` + `imagesRemainGate(platform, md, strict)` 四平台统一收口：转存后正文仍有本地图就打 `⚠⚠` 横幅（写明后果与排查方向），配 `CSPUB_STRICT_IMAGES=1/true/yes` 时返回 true 让调用方 `return 1` 中止，默认仍是 best-effort 照发；③删除被取代的 `hasLocalImages`，其单测用例整组迁进新测试，用例不丢。

**复用配方**：①多平台 CLI 里每个 rehost 函数各打各的计数**不构成告警**，必须有一个统一收口点把「这篇会裂图」翻译成醒目结论；②预演/试运行子命令必须与真实发布走**同一份判定逻辑**（否则预演本身变成误导源），能抽成纯函数就别复制分支；③「是否还会裂图」的判据放在**转存后的正文**上，别信转存函数自己的计数器（跳过的、降级成功的都算不清）；④改行为优先「默认不变 + 环境变量开严格」，一次改动别顺手打断既有的 best-effort 习惯。

## 14. 伴生脚本硬编码相对路径：只有站在仓库根目录才跑得动

**现象**：`--platform baijiahao` 在文章目录里跑，直接报「找不到伴生脚本 `scripts/baijiahao_publish.py`（须在 cspub 仓库根目录下运行）」。掘金图片通道同款问题，但更阴：找不到 `scripts/juejin_upload.py` 就静默降级到内置 ImageX 实现，而 ImageX 直调签名必然被拒（§9），于是**换个目录运行 = 图片全失败**，代价只在日志里留一行 ⚠。

**排查铁证**：①两处调用点都是 `let scriptPath = "scripts/xxx.py"` 再拿 `readTextFileAll` 探测，路径按进程 cwd 解析，与二进制装在哪无关；②从 `/root/test/cj` 跑掘金：出现「⚠ 掘金图片上传脚本不存…降级仓颉内置 ImageX 实现」→ 5 张全失败；③同一条命令在仓库根目录跑 5/5 成功——变量只有 cwd。

**修复方案**：`resolveCompanionScript`（`src/util.cj`）按优先级返回第一个可读候选：①`CSPUB_SCRIPT_DIR` 显式指定；②当前目录的相对路径；③**可执行文件目录起向上回溯 5 级**的 `scripts/<name>`。可执行文件目录用 `canonicalize("/proc/self/exe")` 解析符号链接取得（不依赖 argv[0]），非 Linux 取不到就只走前两个候选。百家号、掘金两处调用点改用该函数，找不到时把三个查找位置与两种修法一起打印出来。候选列表抽成纯函数 `scriptCandidates`，单测不碰文件系统。

**复用配方**：①随二进制分发的伴生文件（python 脚本、模板、数据）**不要用裸相对路径**，按「环境变量 → cwd → 可执行文件目录回溯」三层解析；②Linux 上取自身位置用 `/proc/self/exe` + `canonicalize` 最稳（argv[0] 可能是相对路径或被改写），跨平台留空串降级即可；③「找不到脚本」的报错要直接给出候选路径与修法，别让用户猜 cwd；④降级路径要显眼——本案的降级不是「功能变弱」而是「功能全坏」，一行 ⚠ 挡不住。
