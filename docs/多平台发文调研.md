# 多平台自动发文调研（腾讯云 / 头条 / 小红书 及候选平台）

> 调研时间：2026-11-05
> 目的：为 cspub 从「CSDN 单平台」扩到「多平台自助发文」做技术选型
> 方法：公开资料交叉验证 + **本机实测端点**（无 Cookie 只探测鉴权语义，不发真实文章）
> 结论先行：**推荐顺序 腾讯云开发者社区 → 语雀 → SegmentFault → 51CTO → 头条号 → 小红书**

## 一、结论摘要

| 平台 | 鉴权形态 | 需要请求签名 | 图片策略 | 实现难度 | 建议 |
|---|---|---|---|---|---|
| 腾讯云开发者社区 | 纯 Cookie | 否 | 平台侧转存（qcloudimg） | ★★☆☆☆ | **第一批做** |
| 语雀 | 官方 OpenAPI + Token | 否 | 官方支持 Markdown | ★★☆☆☆ | **第一批做** |
| SegmentFault | Cookie | 否（待抓包确认） | 需转存 | ★★★☆☆ | 第二批 |
| 51CTO | Cookie + JS 反爬挑战 | 可能有 | 需转存 | ★★★★☆ | 第二批（可能要浏览器通道） |
| 今日头条 | Cookie + CSRF Header | 否 | **强制全部转存头条 CDN** | ★★★★☆ | 第三批 |
| 小红书 | Cookie + x-s 签名 + 设备指纹 | **是（AES-128-CBC）** | COS 上传拿 fileId | ★★★★★ | 最后做 |

一句话选型逻辑：**优先挑「没有请求签名、图片要求不苛刻、平台有内容权重」的**。腾讯云和语雀同时满足，是投入产出比最高的两家。

## 二、腾讯云开发者社区

### 2.1 接口（实测确认）

```
POST https://cloud.tencent.com/developer/api/article/addArticle
Content-Type: application/json
Origin:  https://cloud.tencent.com
Referer: https://cloud.tencent.com/developer/article/write-new
```

本机实测两种响应，证明端点真实且**参数校验先于登录校验**：

| 请求体 | 实测响应 |
|---|---|
| `{}`（空） | `HTTP 400` `{"msg":"参数错误","code":400}` |
| 完整字段 | `HTTP 401` `{"msg":"你还未登录，请先登录","code":401}` |

> 这条很重要：只发 `{}` 会得到「参数错误」而不是「未登录」。说明实现时字段必须一次给全，否则拿到的 400 会被误判成「Cookie 失效」。

### 2.2 请求体字段

```json
{
  "title": "文章标题",
  "content": "<p>HTML 正文</p>",
  "plain": "纯文本正文（去标签）",
  "summary": "摘要",
  "userSummary": "用户填写的摘要",
  "sourceType": 1,
  "isOriginal": true,
  "classifyIds": [149],
  "openComment": 1,
  "closeTextLink": 0
}
```

成功响应：`{"articleId":2650368,"status":0}`，`status=0` 即发布成功，文章链接 `https://cloud.tencent.com/developer/article/{articleId}`。

### 2.3 Cookie 字段

从已登录浏览器的 `cloud.tencent.com` 域导出，用分号拼接：

`skey`、`qcloud_uid`、`qcommunity_session`、`loginType`、`qcommunity_identify_id`、`tinyid`（`uin` 可选）。

注意 `skey` 含特殊字符 `*`，Cangjie 侧直接拼接进 `Cookie` 头即可，**不要做 URL 编码**。

### 2.4 约束与坑

1. **正文不少于 140 字**，空正文不能发布（官方文档明示）。
2. **必须归属专栏（`classifyIds`）**：新账号没有专栏时需要先建，且新专栏要审核 1~3 个工作日；每用户自建专栏上限 9 个。这是首次发文的真实卡点——接口能通但可能因无可用专栏失败。
3. **官方文档称发布需选封面**。`addArticle` 是否强制封面需带真实 Cookie 复验；若强制，需补一步封面设置接口。
4. **图片走平台转存**：实测生产文章正文图片域名统计为 `qcloudimg.tencent-cloud.cn`(5)、`qccommunity.qcloudimg.com`(4)、`developer.qcloudimg.com`(4)，全部是腾讯自有 CDN，说明社区会重写图片地址。外链图能否直接留用需实测，**保守做法是发布前把图上传到腾讯云 COS 或接受平台自动转存**。
5. 该接口**没有请求签名**，是全平台里最干净的一个——比 CSDN 还简单（CSDN 需要 `X-Ca-Key` 一整套签名，实测空请求返回 `{"message":"X-Ca-Key is not exist"}`）。

## 三、今日头条（头条号）

### 3.1 接口（实测推翻了网上多数旧教程）

```
POST https://mp.toutiao.com/mp/agw/article/publish
```

本机实测响应：

| 端点 | 实测 |
|---|---|
| `/mp/agw/article/publish` | `HTTP 200` `{"code":100005,"data":{"pgc_id":"0"},"message":"获取用户信息失败","err_no":100005}` ✅ 真端点 |
| `/core/article/edit_article_post/?source=mp&type=article` | `HTTP 502` Bad Gateway（TLB） ❌ |
| `/core/article/add/` | `HTTP 502` ❌ |

> **凡是用 `core/article/edit_article_post` 的教程一律过时**。`100005 获取用户信息失败` 就是「没登录」，带上有效 `sessionid` 才会有真正的发布语义。

### 3.2 鉴权

- Cookie 核心字段：`sessionid`（另有 `csrftoken`）。
- **写请求必须把 `csrftoken` 原值回写到 `X-CSRFToken` 请求头**，否则被判跨站。
- 除 CSRF 外无请求签名，读接口纯 Cookie。

### 3.3 图片：最大的实现成本

头条对图片是硬约束，**不是「建议转存」而是「必须」**：

- 正文里任何 `<img src="非头条 URL">` → 整篇被拒，错误 `7115 图片uri非法`。
- 因此必须：逐张把图片上传到头条 CDN（`mp.toutiao.com` 的上传接口）→ 拿到 CDN 地址与必需属性 → 改写正文 `<img>` 标签 → 再提交。
- 单张上传失败时策略要显式决定：要么中止整篇（原文语义：不静默丢图），要么提供 `--drop-failed-images`。

### 3.4 其他约束

| 约束 | 说明 |
|---|---|
| 标题长度 | **2~30 个加权字符**（ASCII 字母数字按 0.5、空白不计、中文及标点按 1） |
| 每日上限 | 图文约 4 篇/天，超限直接失败，不要重试循环 |
| 发布即入审核 | 返回 URL 需过审才可见；被拒文章在「已失败」里 |
| 修改窗口 | 发布超 14 天不可改 |
| 封面 | 发布流程需要封面（Web 端强制，接口侧需确认） |

### 3.5 难度判定

★★★★☆。接口本身不难（Cookie + CSRF），难在**图片全量转存管线**和**标题加权字符校验**——后者必须在提交前自行算好，否则平台报错信息不友好。

## 四、小红书（创作中心）

### 4.1 接口（实测确认）

```
POST https://edith.xiaohongshu.com/web_api/sns/v2/note
```

本机实测（无签名、无 Cookie）：`HTTP 401` `{"code":-100,"data":{},"msg":"无登录信息","success":false}`

### 4.2 签名：真正的门槛

小红书是全平台里唯一**强制请求签名 + 设备指纹**的：

- `x-s` / `x-t`：创作者域签名，算法为 **AES-128-CBC**——取 `a1` Cookie 前 16 字节作 key、16~32 字节作 iv，加密 `api` 路径拼 JSON body，输出 Base64 签名与时间戳。
- 另有 `x-s-common`、`x-b3-traceid`、`x-xray-traceid`、`x-rap-param` 等一串头。
- 主站（`edith`）用 144 字节的 `x-s`，创作者域用简化版 AES 签名，两者不同。
- **设备指纹必须与 UA 一致**：`a1`、`websectiga`、`b1` 等指纹 Cookie 与浏览器 UA 绑定，UA 对不上直接风控。

### 4.3 图片上传链路

1. `GET /api/media/v1/upload/web/permit`（`biz_name=spectrum&scene=image`）拿 `fileId` + `token`
2. `PUT` 二进制到 COS（带 `X-Cos-Security-Token`，此步无需签名）
3. 用 `fileId` 组装 `image_info` 调发布接口

### 4.4 内容硬约束

| 项 | 限制 |
|---|---|
| 标题 | ≤ 20 字 |
| 正文 | ≤ 1000 字 |
| 图片 | ≤ 18 张，建议 3:4 竖版 |
| 话题 | ≤ 10 个，超出静默丢弃或限流 |
| 封面 | 视频模式必填，图文取首图 |

### 4.5 难度判定

★★★★★。签名算法随前端改版失效（历史上有 `260411`、`251016` 等 JS 版本号迭代），需要持续跟进；且**技术长文不适合小红书**（1000 字上限）。若要做，更合理的是「把文章压缩成摘要 + 拆图做图文笔记」，属于新内容形态而非简单搬运。

## 六、推荐：值得做的几家

按「投入产出比」排序，而不是按流量排序。cspub 的定位是**技术文章分发**，所以技术社区权重高于泛流量平台。

### 第一批：立刻做（预计各 1 天内可落地）

**1. 腾讯云开发者社区** —— 本次调研的最优解

- 接口最干净：纯 Cookie，**零请求签名**，比已支持的 CSDN 还简单；
- 权重高：腾讯云社区文章在中文技术搜索里覆盖率高，且目前没有看到发布频次硬限制；
- 受众匹配：cspub 的使用者写的是技术文章，这里就是目标读者；
- 风险点集中在两处可验证的地方：**专栏（classifyIds）依赖**、**封面是否强制**。两项都能用一次带 Cookie 的真实请求问清楚。

**2. 语雀** —— 长期最稳的一票

- 唯一有**官方 OpenAPI v2 + Token** 的平台，不依赖 Cookie 登录态，不会被前端改版打断；
- 原生 Markdown，几乎零转换成本；
- 实测 `401 Unauthorized` 证明接口在线且规范；
- 缺点：语雀是知识库不是内容分发平台，**换来的是稳定性而不是流量**。适合作为「首发站 + 备份存档」，再用其他平台分发。

### 第二批：值得做（各 2~3 天，需抓包）

**3. SegmentFault** —— 技术受众精准，接口大概率仍是 Cookie 型（只是路径变了），抓一次包就能定位。

**4. 51CTO** —— 老牌技术社区，但实测返回混淆 JS，说明有 JS 反爬。若必须过挑战，得复用现有 Playwright 浏览器通道（`scripts/` 里已有百家号的浏览器方案），成本上升一档。

### 第三批：能做但性价比要权衡

**5. 今日头条** —— 流量天花板最高的一家，但代价明确：**必须自建头条 CDN 图片转存管线**（不做就整篇 7115 被拒）、标题加权字符校验、每日约 4 篇上限、发布进审核队列。适合「文章已经稳定产出、需要拉泛流量」的阶段。

**6. 小红书** —— **建议排在最后，甚至先用替代方案**：签名算法随改版失效需要长期维护，且 1000 字上限与 20 字标题天然不适合技术长文。更现实的做法是「把文章要点压缩成图文笔记」，那是另一种内容生产，不是当前 cspub 的 Markdown 直发能覆盖的。

### 不建议做

- **简书**：接口最容易（Cookie 直发），但平台已明显衰退，分发收益低。
- **网易号 / 大鱼号 / 一点号**：传统媒体号，接口要逐个抓包，读者与 cspub 定位错位。
- **微信公众号**：需要认证订阅号 + 后台 IP 白名单，个人号基本走不通。

### 一句话建议

> **先做腾讯云 + 语雀**（一家拿流量、一家拿稳定），跑通「一份 Markdown 多形态分发」的骨架；再按需补 SegmentFault / 51CTO 扩技术社区覆盖；头条和小红书等有明确流量需求时再投入。

## 七、对 cspub 的工程落地建议

### 7.1 文件切分（沿用 AGENTS.md 的单一职责原则）

```
src/tencent.cj   # 腾讯云社区：addArticle + 专栏/封面前置检查
src/yuque.cj     # 语雀：官方 API v2（Token 鉴权，独立于 Cookie 体系）
src/toutiao.cj   # 头条号：/mp/agw/article/publish + CSRF + 图片强制转存
src/xhs.cj       # 小红书：签名 + COS 上传 + 发布（最后做）
```

不要往 `main.cj` 堆分发逻辑。

### 7.2 先抽公共抽象，再加平台

现有 `src/csdn.cj` / `src/zhihu.cj` 等各自实现发布，平台一多会重复三件事：**front-matter 取值、图片转存、错误归一化**。建议在加第二个平台之前先收敛：

| 抽象 | 说明 |
|---|---|
| 统一发布结果 | `struct PublishResult { platform, articleId, url, draft }`，各平台把自己的响应映射进来 |
| 统一错误语义 | 至少区分：凭证失效 / 参数非法 / 平台限额 / 内容违规 / 网络失败。**头条 100005、腾讯云 401、小红书 code:-1 都要映射到同一套枚举** |
| 图片能力接口 | 复用 `images.cj` 的下载与校验（已含 30x 拒绝、内网拦截、12 MiB 上限），各平台只实现「上传到本平台」这一步 |

### 7.3 逐平台的实现要点

**腾讯云**：字段一次给全（否则 400 会冒充 401）；`plain` 必须是去标签文本；`classifyIds` 建议做成 `cjpm.toml`/front-matter 可配，先用 `[149]` 技术分类，失败时提示「去后台建专栏」。

**语雀**：Token 存独立配置而非 Cookie 文件；`namespace`（知识库）与文档 slug 需要用户配置；Markdown 原样提交即可。

**头条**：先把图片管线做完再谈发布——顺序是「解析正文 img → 逐张上传 → 改写标签 → 提交」。标题长度在本地按加权规则预校验，超限直接给可读错误而不是等平台拒绝。

**小红书**：签名算法要独立成模块并可替换（版本号会变）；设备指纹与 UA 必须成对保存——这点在 `docs/开发文档与踩坑记录.md` 里值得单独记一条。

### 7.4 测试与验证（对齐 CI 红线）

- 每个平台至少一条**离线单测**：给定固定响应 JSON，断言错误映射与字段抽取正确（可以完全离线，用 `*_test.cj`）。
- 签名/CSRF 这类纯函数（小红书 AES、头条标题加权计数）**必须有单测**——它们是「错了就全篇失败」的地方。
- 真机验证沿用现有标准：草稿优先 → 回显 article id → 图片转存后 `curl` 图床直链返回 `200 + 非零字节`。

## 九、SegmentFault 思否（实测已打通端点，2026-11）

这一家与前面几家不同：**不需要登录态就能把接口全查出来**，因为它的前端是 Next.js，
`__NEXT_DATA__` 与静态 chunk 都是公开可读的。做法是读前端源码而不是猜路径。

### 9.1 网关结构：所有请求都是 `/gateway` + 路径

这是最关键的一条，直接决定「为什么网上的 `/api/article/create` 全是 404」。

前端请求封装的原文（`_app` chunk，实测摘录）：

```js
let T = "/gateway" + m;                       // m 是业务路径，如 "/article"
...((_.method) !== "GET" && _.method) || (T = await getUrl(T, this.timeDiff));
```

即：**业务路径拼在 `/gateway` 之后**；且**只有 GET（或未指定 method）才追加时间参数**，
POST/PUT 不加。`timeDiff` 由 `GET /gateway/service/time?query=current` 得到的 `serverTime` 与本地时钟算差。

实测对照（无 Cookie）：

| 请求 | 结果 |
|---|---|
| `GET /gateway/service/time?query=current`（公开接口，对照用） | **200** `{"time":1793916562}` |
| `POST /gateway/article` | **401** `"Unauthorized"` |
| `POST /gateway/draft` | **401** `"Unauthorized"` |
| `POST /gateway/note` | **401** `"Unauthorized"` |
| `POST /gateway/articles` | 404 `"Not Found"`（这条不存在，别用复数） |
| `POST /gateway/article` **不带 Referer** | **403** `"非法请求，请刷新页面后重试"` |

三个结论：
1. `/gateway/article` 路由真实存在，鉴权语义是 **401 `"Unauthorized"`**（不是 403、不是 200 带 code）。
2. **403 是 CSRF 判据**：缺 `Referer`（或 `Origin`）先被网关挡在门外，与登录态无关。
   所以看到 403 不要急着换 Cookie，先补 `Referer: https://segmentfault.com/write`。
3. 判断「路径是否存在」的探针是 **403/401 vs 404**：带 Referer 后 404 才是路径写错。

### 9.2 接口清单（读前端源码得到，与 9.1 的 401/404 实测互证）

```js
postArticle(m)  { return this.request.send("/article",      {method:"POST", data:m}) }  // 发文
saveDraft(m)    { return this.request.send("/draft",        {method:"POST", data:m}) }  // 存草稿
```

| 用途 | 方法与 URL |
|---|---|

### 9.3 鉴权：Token 与 Authorization 同值（双头）

请求头封装的原文：

```js
headers: { Token: C, "Content-Type": "application/json", ...V, ...this.commonParams,
           Authorization: "Bearer " + C }
```

`C` 就是 token，**同一个值既放 `Token` 头、又放 `Authorization: Bearer`**。缺一个都可能被拒。

token 来源是写文章页 SSR 注入的 `serverData.Token`：

```
GET https://segmentfault.com/write   →   __NEXT_DATA__ 里
  "serverData":{"Token":"","userAgent":"...","platform":""}
```

未登录时 `Token` 是**空串**（页面也被换成登录页，`pageProps.initialState.global.sessionUser: null`）。
所以 cspub 的流程是：先用 Cookie 取 `/write` 页 → 抠出 `Token` → 带上双头发 `/gateway/article`。
不能用 cookie 里的某个字段代替，思否没有这类字段。

### 9.4 请求体字段（取自编辑器源码，不是猜的）

编辑器构造草稿体的原文：

```js
{ title, tags, text, object_id, type, language,
  ...(answerMarkdown ? {answer_text: answerMarkdown} : {}) }
if (type === "article") { t.cover = cover }
```

- `text` 是**HTML**（编辑器产出的富文本），不是 Markdown
- `tags` 是**数组**（标签名，不是 id）
- `type` 取 `"article"`（文章）/ 笔记另有其值
- `object_id` 空串表示新文；`cover` 仅文章带，可空

### 9.5 其他实测细节

- **静态 chunk 也要 Referer**：`static.segmentfault.com/.../chunks/xxx.js` 不带 Referer 回 **403（170 字节 HTML）**，
  带上 `Referer: https://segmentfault.com/` 才给真 JS（`_app` chunk 818KB）。这也是「读前端源码」的前提。
- `_buildManifest.js` 里有 **137 条路由**，含 `/Write`、`/write`、`/Note/Write`、`/Draft`、`/HowToWrite`；
  编辑器 chunk 是 `pages/Write-1968a88a72716030.js`（28KB，UI 层，不含接口路径——接口在 `_app` 里）。
- 业务路径里的 `/api/name`、`/api/hot_tags` 同样走 `/gateway` 前缀，所以完整地址是
  `/gateway/api/hot_tags`；直接请求 `/api/hot_tags` **404**（实测）。

### 9.6 难度判定

**低**。零签名、零浏览器、零 JS 逆向，只需要「取页抠 token + 双头 + 双 Referer」。
唯一不能离线确定的是成功响应的具体形状（登录后才能拿到），所以状态记为
「端点/鉴权/字段已实测，成功响应形状待凭证验证」。

## 十、51CTO 博客（实测撞墙：登录前无法确定发文接口）

### 10.1 反爬：`__tst_status` 挑战（常量每次变）

`GET https://blog.51cto.com/blog/manage/article/add` 未带挑战 cookie 时回 **988 字节混淆 JS**，

其中 `a(0)` / `a(1)` 由内联常量算出（`WTKkN` / `bOYDu` / `wyeCN` + 一个加法常量）。

|---|---|---|---|
| 第 1 次 | 1616694121 | 293286005 | 2155888083 |
| 第 2 次 | 828088152 | 1051234273 | 2186545784 |

首页是纯 SSR（`<script src>` 数量为 0），没有可反查的编辑器 bundle；

按 AGENTS.md 的红线「不允许先交付后补测」「行为变更必须有对应测试」，
这家的请求体没有任何实测样本，写出来只能是编造，**故 cspub 不提供 51cto 平台**。
要推进需要一次性抓包（登录后手动发一篇，复制发文的完整请求与响应），拿到后约半天可落地。

> 前提是先用一个已知公开接口（SegmentFault 的 `/gateway/service/time`、51CTO 的 `/api/welcome`）
> 证明网络与反爬都通——否则分不清「路径错」和「被挡」。

### 11.3 腾讯云 RPC 打通全记录（2026-11-06 续，真实草稿 draftId 341903）

**① 真实端点**（`/services/ajax/{ns}` 全 501 的病根在 namespace 带斜杠且路径含 `developer/`）：

```
POST https://cloud.tencent.com/developer/services/ajax/column/article?action=CreateArticleDraft&uin=<uin>
Content-Type: application/json
Cookie: <整串>

{"action":"CreateArticleDraft","payload":{...12 个字段...}}
```

- `uin` 从 Cookie 的 `uin=o100009199133` 取，**前导 `o` 要去掉**（保留会是无效账号）。
- `csrfCode` **可带可不带**：实测不带 `csrfCode` 同样 `code:0`（原以为必需，抓包里那个 `csrfCode=922865963` 只是样本值）。
- 鉴权只认 Cookie，零签名。

**② `content` 是三层编码**，错一层就 400：

```
content = base64( urlencode( JSON.stringify( jsonpack.pack(rawDraftContentState) ) ) )
plain   = base64( urlencode( JSON.stringify(纯文本) ) )
```

`rawDraftContentState` 是 Draft.js 的 `{blocks, entityMap}`；`jsonpack.pack` 把字段名压成字典下标（`"blocks|key|421q5|text|..."`），必须与官方 `jsonpack` 的字典构造顺序逐字节一致，否则服务端能存、编辑器读不出来。
仓颉移植版 `src/jsonpack.cj` 的单测直接拿**线上真包原文**当基准（见 ③），不是「能存进去就算过」。

**③ 三变体实测（同一端点、同一 Cookie）**：

| 变体 | content 形态 | 结果 |
|---|---|---|
| A | 未压缩 raw JSON | `{"code":400,"msg":"文章草稿创建失败，请稍后重试 [400]"}` |
| B | `base64(urlencode(jsonpack.pack))` | `code:0, draftId:341899` ✅ |
| C | `base64(urlencode("纯文本"))` | `code:0, draftId:341900` ✅ |

结论：服务端只要求 `content` **是字符串**（压缩非强制），但为让编辑器正确加载正文必须用 jsonpack。
用户抓包里的真值可直接当测试基准：`content` 解码即
`"blocks|key|421q5|text|aaaaaa|type|unstyled|depth|inlineStyleRanges|entityRanges|data|entityMap^0^^$0|@$1|2|3|4|5|6|7|C|8|@]|9|@]|A|$]]]|B|$]]"`，

`300031 / -9993`——说明参数校验已过，400 那个字段就是它，不必猜。

成败铁证：`--live` 回显 `articleId 2777717` + 文章地址；带登录态 GET 文章页 `200 / 68380B`，标题
`cspub：一份 Markdown 发遍多平台-腾讯云开发者社区-腾讯云`；草稿 `341912` 已从 `FetchArticleDrafts` 的 12 条里消失，
证明服务端**确实按 `draftId` 转正、没有多建一篇**（此前担心的「被当新建」不成立）。

**⑧ 专栏与标签怎么查**（默认 149 在多数账号上不可发）：专栏列表不在 `column/article`，而在
`column/column`——`FetchJoinedColumnList` 返回本账号已加入专栏（本例 `88542`，`isJoin:1`），
`FetchColumnTags` 返回该专栏标签（本例 177 个，如 `10757 markdown`、`17183 编程`）。配
`CSPUB_TENCENT_CLASSIFY_IDS=88542` + `CSPUB_TENCENT_TAG_IDS=10757,17183` 即可发布；两者都从环境变量或
`~/.cspub/config.json` 读。

**⑨ 顺带修掉的两处文案债**：`--draft` 不再是 dry-run（真存草稿）；`whoami tencent` 的登录态判据多了 `uin`。

### 11.4 结论与续做配方

**腾讯云已经闭环**：草稿、图片转存、正式发布三条链路都在真机上跑通（`draftId 341903/341905`、
`articleId 2777717`），不再需要抓包。回头看不必要的等待都来自一个误判——以为「没抓包就不敢动」，
而这轮的 five 个坑（⑦）全部靠**读 bundle + 逐字段删重发**定位，没有一个需要真实抓包。

**头条号也已闭环**（2026-11-06 续）：发布成功 `pgc_id 7704932867448603187`，先 `status=6 审核中`、
数分钟后自动转 `status=3 已发布`，公开页 `HTTP 200`；图片转存回显「成功 2，失败 0」，转存直链
`curl` 回 `HTTP 200 / PNG`。三处定因同样不靠抓包：①`7050` = body 必须 form-urlencoded；
②图床上传必须 `?type=json…` + 尾斜杠 + `x-requested-with: XMLHttpRequest`（缺任一恒 `1050`）；
③**`save=1` 不是存草稿而是提交即发布**——这条最贵，`--draft` 曾长期静默公开发文。

**头条的 `save` 语义已彻底查清（2026-11-06 拿到真实编辑器抓包后复验）**：抓包给了三段真实请求——
草稿列表 `GET /mp/agw/creator_center/draft_list?type=0&count=20&app_id=1231`、草稿读取
`GET /mp/agw/article/edit?pgc_id=…&format=json`、以及编辑器「点发布」的 `publish`（`save=0` + 25 个字段 +
`msToken`/`a_bogus`/`tt-anti-token`/`x-secsdk-csrf-token`）。据此做完整 A/B：

| `save` | 回执 | 落点 |
| --- | --- | --- |
| `0` | `7050`（带齐全套字段 + 原样风控值也仍是 7050） | 无——风控产物一次性，重放即失效 |
| `1` / `3` / `4` | `code 0` + `pgc_id` | `审核中` → `已发布`，公开页 200 |
| `2` | `5009 发布失败` | 无 |

结论：**头条的真草稿箱确实存在（`draft_list` 里 17 条，全部由编辑器自动保存产生），但纯 HTTP 脚本写不进去**
——`save=0` 要 webmssdk 签名、`save_ugc_draft` 是 `1066`/`1064`。所以 `--draft` 对头条保持「安全拒绝 + 打印证据」，
`--live` 用免风控的 `save=1`。这不再是「待抓包」的缺口，而是**已确认在无浏览器环境下不可实现**。
另记一个容易误判的点：公开页路径以 `/article/<pgc_id>/` 为准，老路径 `/item/<pgc_id>/` 已 404。

> 通用教训：**「我的字段看起来挺全」不是证据**。腾讯云这轮最贵的一课是——先确认接口还在不在用
> （`grep addArticle` 在前端 bundle 里是 0 次），再去调字段；否则会一直在一个已被前端淘汰的端点上做参数实验。
